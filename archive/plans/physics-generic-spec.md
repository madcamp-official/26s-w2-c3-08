이전 문서 [physics-rework-plan.md](physics-rework-plan.md)의 논의를 이어받아 확정한 최종본.
이전 브랜치(`kjh/baseworld-netphysics`, 커밋 `640ee96`)의 **로직은 최대한 배제**하고,
개념·구조만 가져와 새로 짠다. 이 문서는 실제 구현 착수 시 기준 스펙이며, 실행(파일 작성)은
별도 "승인"을 받은 뒤 진행한다.

> **⚠️ 최상위 방향 전환 (2026-07-12 확정 — §14 필독)**: 원격 실측(입력→반영 왕복 평균
> 305ms)으로 서버 권위 강한 모델이 조작감을 못 살린다는 게 드러남. **서버를 "중계기(relay)"로
> 격하하고, 각 클라이언트가 자기 캐릭터에 대한 로컬 권위를 가진다.** 핵 방지는 포기.

## 2. Body 타입 (범용 물리체)

```typescript
interface Body {
  x: number; y: number;       // 원점 = 바닥-중앙 (§8, 좌상단에서 변경)
  vx: number; vy: number;
  w: number; h: number;       // 히트박스 크기 — 엔티티마다 다를 수 있음
  grounded: boolean;
  facing: 1 | -1;
  touchingWall: 0 | 1 | -1;
  onSlopeDir: 0 | 1 | -1;
  gravity: boolean;           // 중력 적용 여부 (직선 발사체는 false 가능)
  tags: string[];              // "player" | "enemy" | "platform" | ... → interactions.ts 매칭 키
}
```
플레이어의 능력 상태(`pound`, `spin`, `crouch`, `slide`, 타이머류)는 이 `Body`를 감싸거나
포함하는 형태로 `entities/player/state.ts`에 둔다. 확장(상속) vs 합성 중 무엇으로 할지는
구현 시점에 결정.

## 3. 겹침 해소 — MTV(최소이동벡터) 방식 확정

### 배경 — 발견된 버그
구식(이전 브랜치) 방식은 겹쳤을 때 `vx` 부호만 보고 "어느 쪽에서 왔는지"를 추측해 그 방향으로
강제 이동시켰다. 이미 겹친 상태(낑김)에서 시작하면 추측이 틀려 반대쪽으로 크게 튕기는 "순간이동"
버그가 발생함을 직접 시뮬레이션으로 확인(2026-07-11/12 진단, `x=290`→`x=236` 54px 순간이동 재현).

### 낑기는 경로 (확인된 원인들)
1. **밟기(headStand/stomp)의 y 스냅** — `a.y = bTop - H` 겹침 검사 없이 강제 이동
2. **밀기(resolvePush)의 x 이동** — 겹침 검사 없이 벽 안으로 밀어넣는 버그(별도 확인됨, §5)
   → 이 두 버그가 이어져서 "밀려서 벽에 박힘 → 움직이면 순간이동"이 실제로 재현되는 주 경로
3. `tp` 콘솔 명령 — 개발용, 겹침 검사 없음(의도적)
4. 웅크리기→서기 전환의 `standingOk()` — 경사면(`slopes`) 미검사 결함 확인됨

### 해법 — 실제 겹침 깊이 비교
```
overlapLeft  = (박스A 오른쪽 끝) - (박스B 왼쪽 끝)
overlapRight = (박스B 오른쪽 끝) - (박스A 왼쪽 끝)
→ 더 적게 겹친 쪽으로, 그 겹친 양만큼만 밀어냄
```
속도 부호를 신뢰하지 않고 항상 실제 겹침 크기만큼만 이동하므로, 낑긴 상태에서 시작해도
큰 순간이동이 원리적으로 발생하지 않는다. `body.ts`의 `moveAndCollide()`에 이 방식으로 구현.

**단, 근본 해법과 별개로 1·2번(밟기 y스냅, 밀기 x이동)의 겹침 검사 누락 자체도 고쳐야
낑기는 빈도 자체가 줄어든다** — MTV는 "낑겨도 안전하게 풀리는 것"이지 "낑기지 않게 하는 것"은
아니므로 둘 다 필요.

## 4. 파괴형 블록 — 지형 계층에 흡수

**출처 확인됨** — [asset-attributes.md:80-94](../../docs/KJH/asset-attributes.md) 원문에
이미 기획되어 있었음 (새 결정 아님, 기존 결정을 물리 구조에 반영하는 것):

| 접촉 반응 [택1] | 내용 |
|---|---|
| 없음 (기본) | — |
| 닿으면 2초 후 낙하 → 5초 후 재생 (고정) | 도넛 블록 방식 |
| 닿으면 2초 후 파괴(소멸) → 5초 후 재생 (고정) | 자체 기획 |

**확정 규칙 (원문)**: 플레이어에 의한 직접 파괴(타격 파괴)는 제거됨 — 유저 제작 에셋 + 다수
동시 플레이 + 라인 랜덤 연결 특성상, 영구 파괴는 뒷순번 플레이어 진행 불능(소프트락) 위험.
**재생은 옵션이 아니라 항상 고정 재생.**

### 구조적 결정 — "흡수"의 의미
블록을 `entities/block/`처럼 별도 엔티티 폴더로 만들지 않고, `terrain.ts`에 `Rect`/`Slope`와
같은 급의 데이터 타입으로 정의한다:
```typescript
interface DestructibleBlock {
  rect: Rect;
  contactSides: Side[];         // 감지 면, 기본값 상면만
  mode: "fall" | "vanish";
  delayMs: number;               // 고정 2000
  respawnMs: number;              // 고정 5000
  state: "idle" | "triggered" | "gone";
  stateElapsedMs: number;
}
```
이유: 블록은 `Body`처럼 스스로 속도를 갖거나 입력을 받는 존재가 아니라, 위치 고정 +
상태·타이머만 있는 "지형의 시간에 따른 변형"에 가깝다. 지형 조회 계층이 이 상태를 같이 보고
"gone" 상태면 충돌에서 제외한다.

## 5. 상호작용 계층

### player-vs-player (`entities/player/interactions.ts`)
- **밀기**: 지형 재검사 포함하도록 수정 (구식은 겹침 검사 없이 벽 안으로 밀어넣는 버그 있었음)
- **밟기**: 밟는 쪽의 낙하속도가 `stomp.minFallSpeed` 이상일 때만 발동. 미만이면 머리 위
  안정적으로 서기(headStand)로 지지
- **머리서기(headStand)**: 클라 예측에서도 실행 가능 (상대 좌표만 있으면 되므로)

### 밟힘 시각 동기화 — rideOffset (§6에서 상술)
밟힌 쪽이 스쿼시 연출로 시각적으로 쭈그러들면, 밟은 쪽은 물리 좌표가 아니라
**밟힌 쪽의 실제 그려지는 상단**을 따라가야 공중에 뜬 것처럼 안 보인다. `netphysics/rideOffset.ts`가
이를 일반화해서, 향후 이동 발판 탑승과 같은 메커니즘으로 처리한다.

### 향후 필요 (미착수, 목록만)
- player-vs-enemy, player-vs-platform, projectile-vs-enemy 등 태그 조합별 규칙
- `interactions.ts`의 `InteractionRule` 인터페이스로 등록되는 구조

## 8. 좌표계 확정 — 바닥-중앙 원점으로 변경

이전 브랜치는 좌상단 원점(`p.y` = 서 있을 때 히트박스 상단, 발 = `p.y + H`)이었음.
**이번에 바닥-중앙(발이 닿는 지점, 좌우 중앙) 원점으로 변경 확정.**

이유:
- 좌상단 방식은 웅크리기/슬라이딩으로 키가 바뀔 때 "발 고정, 상단만 이동"을 위해 매번
  `off = H - effH` 같은 보정값을 계산해야 했음 (실제로 이전 브랜치 `integrate()`에 있던 코드)
- 바닥-중앙이면 서 있을 때 상단 = `y - H`, 웅크렸을 때 상단 = `y - effH` — 보정값 불필요
- 스폰·순간이동·블록 배치가 "이 좌표에 서 있다"로 직관적으로 일치
- 밟기 판정(상대 머리 위에 세우기)도 "상대의 발 기준 위치" 역산이 불필요해짐
- 렌더링에서 좌우 중앙 정렬을 위한 `x + W/2` 계산도 사라짐(이미 중앙이므로)

충돌 판정 코드는 `x, x+w` 대신 `x - w/2, x + w/2` 형태로 조정 필요 (사소한 변경).

**좌표는 연속적(부동소수점 px)** — 정수 타일 좌표가 아님. 타일(64px)은 스프라이트 캔버스
크기·맵 에디터 배치 격자 기준일 뿐, 실제 이동은 매 틱 가속도 적분으로 소수점 값을 그대로 가짐.

## 9. 플레이어 물리 수정 사항 (확정)

- **트리플 점프 삭제**
- **벽점프 시 스핀 쿨타임 리셋** — 원작 확인(오디세이: "스핀 점프를 벽점프로 연결 가능", 즉
  벽점프는 새 점프 동작이라 스핀이 다시 허용됨). 착지해야만 리셋되던 버그 수정
- **스핀 시각효과 단순화** — 가로 스케일 왕복(뒤집기) 제거, **색상만 변경**. 내려찍기 hang의
  평면 회전(앞구르기)은 원작 일치이므로 유지
- **내려찍기 최소 높이** — "grounded가 false로 바뀐 순간의 y좌표"(`airborneStartY`)를
  `Body`(또는 능력 상태)에 저장, `|현재y - airborneStartY| >= pound.minHeightPx` 이상일 때만
  발동. 점프뿐 아니라 걸어서 낭떠러지에 떨어진 경우도 자연히 커버
- **슬라이딩 첫 속도 이슈 원인 확인** — 내려찍기는 낙하 중 매틱 `vx=0` 강제 → 경사 착지로
  슬라이딩 전환 시 vx=0에서 재가속(3200px/s²)해야 해서 시작이 굼뜸. 원작(NSMB Wii)은 상한 없이
  경사를 넘나들며 계속 가속(4.07→4.15→4.3배속) — 우리는 `slide.maxSpeed` 상한 있음(단순화,
  변경 여부 미결정)
- **코요테 타임/점프 버퍼는 이미 구현되어 있었음** (80ms/100ms) — 별도 작업 불요.
  "턱을 간발의 차로 넘는" 체감의 원인일 가능성 있는 후보로 남겨둠(직접 재현은 실패)

### 미해결 — 턱 자동 상승 현상
시뮬레이션으로 "축분리 충돌 부작용" 가설을 재현 시도했으나 **재현 실패**. 정상적으로
막혀서 미끄러져 떨어지는 것만 확인됨. 남은 후보: ①클라-서버 보정(reconcile) 부작용(서버 계산이
클라 예측보다 관대하게 나온 경우 스냅되며 도움받은 것처럼 보임) ②코요테타임/점프버퍼의 의도된
관대함. 확답 못 함 — 실제 클라·서버 동시 구동 환경에서 재확인 필요.

## 14. ★ 네트워크 모델 대전환 — relay 서버 + 로컬 권위 + 2레이어 상호작용 (2026-07-12 확정)

이 절이 §5(상호작용)·§6(netphysics)의 서버 권위 전제를 **덮어쓴다**. 앞 절들은 로컬 검증 흐름
설명으로만 참고하고, 실제 구현은 이 절 기준.

### 14-0. 계기 — 원격 실측
- cloudflared 터널 경유(대전 노트북 기준) headless 프로브 측정: **입력→서버반영 왕복 평균 305ms,
  p95 323ms**. 상태 패치 수신 평균 51.6ms 간격
- 이 지연에서는 서버 권위 + 오차보정(LERP/스냅)으로는 조작감을 못 살림 — 끌림·순간이동 상시 발생
- 결론: 서버 권위를 근본적으로 약화. 핵 방지 포기(사용자 명시 동의)

### 14-1. 서버 = 중계기(relay)
- 서버는 각 클라가 보낸 자기 위치·상태를 **검증 없이 다른 클라에 전달만** 함
- 물리의 진실은 각 클라이언트. "내 캐릭터는 내가 결정" (로컬 권위)
- 상대 플레이어는 내 화면에서 **고스트**(서버가 받은 위치를 보간한 프록시). 내가 직접 안 움직임
- 장점: 지연과 무관하게 내 캐릭터가 0ms 반응. 단점: 핵 가능(자기 위치 조작) — 포기하기로 함
- 블록 파괴/재생(§4)은 예외적으로 **서버 권위 유지 검토**: 시간 기반이라 결정론적이고, 5초 재생이라
  지연이 티가 덜 남. "누가 먼저 트리거했나"의 클라 간 불일치를 서버가 정리하는 게 나음 (미확정)

### 14-2. 통일 원칙 — "당하는 쪽이 판정을 확정한다"
모든 상호작용(밟기·밀기)에 공통 적용:
> 공격하는 쪽은 자기 화면에서 **연출과 손맛만 즉시** 받는다.
> 실제 피해/밀림(좌표·속도 변경)은 **당하는 쪽 클라가 자기 화면 기준으로만** 확정한다.

- player-spec.md의 "밟히는 쪽 디메리트는 서버 또는 피해자 클라가 중재"에서 **중재 주체를
  피해자 클라로 확정**한 것. 문서와 어긋나지 않음
- 트레이드오프가 favor-attacker와 정반대로 뒤집힘:
  - 없어지는 것: "접촉 안 했는데 밀렸다/죽었다"(억울한 피해) — 피해자는 자기 화면에만 반응하므로 0
  - 새로 생기는 것: **"내 화면엔 맞았는데 상대에겐 안 맞음" = 공격이 가끔 씹힘** (지연 클수록 증가)
  - 사용자 판단: 억울하게 당하느니 가끔 공격 씹히는 게 낫다 → 이 트레이드오프 수용

### 14-3. 2레이어 분리 — 연출 vs 실제 상태
모든 상호작용을 두 층으로 나눈다.

**A. 연출 레이어 (스프라이트만 이동, 진짜 좌표 불변)**
- 각자 **자기 화면에서 접촉 감지 시** 트리거 — 항상 나옴
- **상대의 실제 상태와 무관한 순수 시각 피드백** (= "선의의 거짓말", 사용자 명시 승인).
  미는 사람 화면에선 상대가 실제로 안 밀려도 상대 스프라이트에 찌부 연출이 나옴 → 손맛 보장
- 밟기: 밟힌 사람 스프라이트 스쿼시(쭈그러듦→펴짐) + 밟은 사람 스프라이트가 그 머리 위로 내려감
  (= rideOffset, §6). 진짜 좌표는 안 변하므로 밟은 사람이 공중에 뜬 것처럼 안 보이게 함
- 밀기: 미는 사람 화면 → 당한 사람 스프라이트가 밀린 방향으로 찌부. 밀린 사람 화면 → 자기
  스프라이트가 그 방향으로 밀린 오프셋
- **원복 방식(확정)**: 지속 접촉 동안 밀린 오프셋을 **유지**하다가, 접촉이 끝나면 원복
  (매 틱 튕겼다 원복 반복이 아님)

**B. 실제 상태 변경 (진짜 좌표/속도 변경)**
- **당하는 클라가 자기 화면 기준으로만 판정**
- 밀기: 밀린 사람 화면에서 상대 고스트가 실제로 자기 몸과 겹쳤을 때만 진짜로 밀림
  (= "각자 자기만 밀어냄". 상대 고스트는 안 건드리고 내 몸만 겹침 해소)
- 자기 화면에서 접촉이 없으면(지연으로 안 겹쳐 보이면) → 실제 밀림 없음 + 연출도 없음
  (접촉 트리거 자체가 안 됨)

### 14-4. 밀기 상세 — 양쪽 화면 대조 (한 번의 밀기)
| | 미는 사람 A 화면 | 밀리는 사람 B 화면 |
|---|---|---|
| A 위치 | 실제 좌표(내 물리) | 고스트(보간) |
| B 위치 | 고스트(보간) | 실제 좌표(내 물리) |
| 접촉 판정 | A가 B고스트와 겹침 | B가 A고스트와 겹침 |
| 연출(A) | B고스트 스프라이트를 찌부(순수 연출) | — |
| 연출(B) | — | 자기 스프라이트 밀린 오프셋 |
| 실제 변경 | A 자신이 막힘(자기 지형·겹침 처리) | B가 자기 화면 겹침 시에만 실제 밀림 |

- 벽 클립 없음: B의 지형 충돌은 B 클라가 처리 → 벽 뒤로 밀어넣어질 수 없음
  (이전 브랜치 resolvePush 벽클립 버그의 근본 해소)
- 능동적 밀기 세기: "상대가 저항해도 밀리는가"는 **밀어내기 속도 vs 이동속도 튜닝** 문제로 귀결.
  밀어내기를 이동속도보다 세게 잡으면 저항해도 밀림, 약하면 저항으로 버팀 → tuning.json + tune

### 14-5. 밟기 상세
- 밟은 사람: 자기 화면에서 밟았다 판단 시 즉시 튕겨오름(로컬 권위) + 연출(자기 스프라이트가 상대
  머리 위로 rideOffset)
- 밟힌 사람: 자기 화면에서 상대 고스트 발이 자기 머리에 닿았다고 판단될 때만 디메리트(하강) 적용.
  스쿼시 연출은 자기 화면 접촉 시 재생
- favor-attacker가 아니라 §14-2 통일 원칙(당하는 쪽 판정) 적용 — 밟기도 씹힐 수 있음

### 14-6. 구조 반영 (기존 §1·§5·§6 갱신점)
- `shared/physics/interactions.ts`: "서버 권위 판정" 전제 삭제. 대신 각 클라가 **자기 캐릭터에
  대해서만** 상호작용을 로컬 실행하는 형태로 재정의. "당하는 쪽 판정" 규칙을 여기 인터페이스로
- `entities/player/interactions.ts`: 밀기=각자 자기만 밀어냄(내 몸만), 밟기=당하는 쪽 판정.
  능동적 밀기 힘은 별도 전송 없이 "상대 고스트와 겹치면 내가 밀림"으로 자연 발생
- `client/src/netphysics/`:
  - `predict.ts` — 자기 캐릭터 로컬 물리(권위). 서버 보정으로 덮어쓰지 않음
  - `interpolate.ts` — 상대=고스트 보간 (변경 없음, 오히려 이게 주역이 됨)
  - `reconcile.ts` — **역할 축소/재정의**. 서버 권위가 없으므로 "서버 값으로 자기 위치 보정"은
    안 함. 대신 자기 위치를 서버(relay)에 송신하는 역할, 그리고 큰 이상치(치트 방지 최소한이
    필요하면) 정도만. input-replay 롤백은 로컬 권위라 불필요해짐
  - `rideOffset.ts` — 연출 레이어 A의 핵심. 밟힘 스쿼시 추종 + 밀기 오프셋 + (향후)이동발판 탑승
  - **신규 검토**: `squash.ts` 또는 rideOffset에 통합 — 연출 레이어(찌부·밀림 오프셋·스쿼시)를
    상대 상태와 분리해서 "자기 화면 접촉"으로만 구동하는 모듈
- 서버 `PhysicsRoom`: "고정틱 물리 시뮬레이션"에서 **"위치·이벤트 중계 + (선택)블록 권위"**로
  성격 변경. 서버가 플레이어 물리를 안 돌림 (블록 등 결정론적 오브젝트만 서버가 돌릴 수 있음)

### 14-7. 남은 미확정
- 블록 파괴/재생을 서버 권위로 둘지 vs 각 클라 결정론 계산으로 둘지
- relay 서버에서도 최소한의 치트 가드(순간이동 등 명백한 이상치)를 둘지 — 순수 relay면 0
- 능동적 밀기 세기 기본값(밀어내기 vs 이동속도 비율)
- 밟기 "씹힘" 빈도가 실제로 얼마나 거슬리는지 — 원격 실측 후 재평가

## 15. 벽 타기 (신규 사양, 2026-07-12 확정)

### 15-1. 동작
- 벽 접촉 **시작 순간** 낙하 속도를 리셋: `vy = 직전_vy × wallGrab.enterPercent`
  - 고정 상한(이전 브랜치의 slideMaxFall clamp) 방식 **폐기**. 진입 속도에 비례해서 줄임
  - **enterPercent 기본 30%, tuning.json 퍼센트값 → tune으로 조절**
- 리셋 후 중력으로 **재가속**하며 미끄러져 내려감 (붙잡혔다 스르륵 내려가는 느낌)
- 근거: 벽 타기는 경사 슬라이딩과 달리 속도 경쟁이 아니라 이동/붙잡는 수단 → 속도감보다
  "붙잡는 느낌"이 중요

### 15-2. 발동 조건 (벽 클링 코요테)
- 벽 방향 이동 입력 시 붙음
- **반대 방향/무입력이어도 유예시간(약 120ms) 동안은 벽에 유지** → 벽점프 타이밍 관대화
- 유예시간 tuning 항목

### 15-3. 미확정
- 재가속 상한: 명시 안 됨 → 일단 일반 낙하속도(maxFallSpeed)까지. 추후 벽 전용 상한 추가 가능

## 16. 스핀 관련 최종 정리 (원작 조사 반영)

### 16-1. 공중 스핀(Midair Spin)만 채택
- **스핀 점프(지상 발동 특수 점프)는 넣지 않음** — 원작 조사 결과 별개 기술이나, 우리 게임에
  대응되는 효과(밟기 불가 적 밟기·블록 파괴)가 없어 불필요
- 공중 스핀 = 공중에서 점프키 재입력 시 발동, 낙하 감속(체공 연장)
- **1회 제한, 리셋 조건 = 착지 / 벽점프 / 벽 슬라이드 시작** (오디세이가 벽 슬라이드를 리셋
  조건에 포함한 것 반영)

### 16-2. 내려찍기·스핀 연출 = 애니메이션 스프라이트로
- **코드 평면 회전(플립) 폐기** — 별로임(사용자)
- 내려찍기 hang 동안 **"스핀" 애니메이션 스프라이트** 재생 (나중에 AI 생성)
- ⚠️ **스프라이트 규격 영향**: player-spec의 애니메이션 idle/walk/onair 3종에 **"스핀"이
  추가 종류로 필요**해짐. asset 생성 파이프라인·규격에 반영 필요 (KJH↔LSJ 접점)

## 17. 자기 변형(스쿼시/찌부) — 전 엔티티 공통 속성 + 방향성

### 17-1. 핵심 원칙
- **자기 변형은 무조건 연출 (실제 위치·히트박스 절대 불변)**. §14-3 연출 레이어의 일부
- **플레이어만의 것이 아니라 모든 엔티티의 속성** — 발판·스프링·블록이 각자 자기 변형 규칙을 가짐
- 변형에 **방향(받은 힘의 방향)**이 있어야 함:
  - 밟힘(위에서) → 세로 눌림
  - 밀림(옆에서) → 가로 찌부
  - 스프링/아래→위 충격 → 해당 방향 변형
  - 즉 "어느 방향에서 힘을 받았나"에 따라 변형 축·방향 결정
- `squash.ts`(연출 모듈)는 방향 벡터를 갖는 변형으로 설계

### 17-2. rideOffset — 일반화 + 변형은 속성으로 분리
- rideOffset = "접촉한 대상의 **그려지는 표면**을 추종한다"는 하나의 일반 메커니즘.
  분기 없이 발판·스프링·플레이어를 같은 코드로 처리
- 대상별 차이("내 표면이 지금 어디냐")는 **각 엔티티/블록의 자기 변형 속성**에서 나옴:
  - 이동 발판: 변형 없음 → 탑승자는 발판 실제 이동량만 추종
  - 스프링/트램펄린: 눌림 변형 있음 → 탑승자는 눌린 표면 추종
  - 밟힌 플레이어: 스쿼시 있음 → 밟은 사람은 줄어든 스프라이트 상단 추종
- [asset-attributes.md](../../docs/KJH/asset-attributes.md)에 이미 "스쿼시 연출", "밟으면 튕김
  (반발력 n)" 옵션 있음 → **"밟혔을 때 변형하는가 / 그 변형을 탑승자가 추종하는가"를 그 속성
  체계에 연결**

## 18. "지형도 엔티티" — 통합 관점 (중요)

지형·플레이어·발판·적·블록을 전부 **동일하게 엔티티로 취급**한다. 구조상 다를 게 없음:
- **모두 Body 기반** (혹은 Body 성격 공유): 위치·히트박스·tags 보유. 종류 구분은 `tags`로만
- **모두 연출(스프라이트) vs 실제(히트박스) 2층을 가짐**: 지형도 보이는 모습≠판정 박스 가능
  (경사, 파괴형 블록 낙하 연출 등) — 플레이어의 스프라이트≠히트박스와 완전히 동형
- **모두 서버 수신 상태를 가짐**: 파괴형 블록도 "서버 기준 gone인가"가 클라와 다를 수 있음
- **자기 변형(연출)도 전 엔티티 공통**
- 정적 엔티티(지형·블록) vs 동적 엔티티(플레이어·적·발판) 구분은 가능하나, serverview·연출·
  판정 관점에선 구분 없이 다 엔티티

용어: **엔티티(entity)**가 맞는 통칭. Body + tags 기반이라 정확.

## 19. serverview — 범용 디버그 뷰어 (재정의, 확정)

새 relay 모델에서 "서버 원본"이라는 단일 권위 좌표가 없어졌으므로 재정의. serverview는
"플레이어 디버그"가 아니라 **모든 엔티티의 연출/판정/네트워크 3층을 태그로 필터해 보는 범용 뷰어**.

### 19-1. 명령 구조
```
serverview [주체] [옵션들]
```
- 주체를 먼저 적음: `serverview player 1 2 3` = 플레이어만, 옵션 1·2·3
- **주체 생략 = 지형 + 플레이어 전부(모든 엔티티)**: `serverview 1 2`
- 주체는 tags로 필터 (player / terrain / block / ...)
- **기본 상태(serverview 끔) = 진짜 인게임 화면만.** 스프라이트 없는 현재는 serverview 안 켜면
  지형 외 아무것도 안 보이는 게 정상

### 19-2. 세 옵션 (독립 토글, 겹쳐 켤 수 있음)
- **옵션1 — 스프라이트 박스**: 인게임에서 실제로 **보여지는 모습(연출 적용된 스프라이트)**을
  감싸는 박스. 매우 투명하게. 웅크리면 1타일로 줄어든 스프라이트 크기를 따라감. 밀림·스쿼시
  같은 연출 오프셋도 반영(보이는 걸 그대로 감싸므로)
- **옵션2 — 히트박스**: 실제 물리 판정 박스. **불투명한 진한 테두리**(채움 아님), 색은 소속별
  유지(본인 파랑 등). 웅크리면 스프라이트는 1타일이지만 이 박스는 0.95타일.
  → 옵션1+2 동시에 켜면 "보이는 것 vs 판정"의 차이가 눈에 보임
- **옵션3 — 서버 수신 상태**: 서버(relay)에서 받은 위치·상태 기준 히트박스를 초록 계열로.
  **내가 받은 "나 자신" 위치 = 청록색**(내 로컬 진실과 벌어진 정도 비교), **남들 = 연두색**.
  위치·크기뿐 아니라 **서버에서 받은 상태 전부(pound/crouch 등)를 박스 모양에 반영**
  (서버 기준 웅크림이면 초록 박스도 0.95). **플레이어 외 엔티티도 동일**(블록의 서버 기준
  gone 여부 등)

### 19-3. help 출력에 옵션 설명 포함 (필수)
- `help`(또는 serverview 도움말)에서 옵션 1·2·3이 각각 무엇인지 위 설명을 반드시 출력
- 겹쳐 켜는 법, 주체 필터, 색 규약(청록=내 서버수신, 연두=남 서버수신, 소속색=로컬 히트박스)도 안내
- 명령 형태(다시 치면 토글 off, 전체 off 방법 등)는 구현 시 확정

## 21. 몬스터 모델 (완결)

### 21-1. 권위
- **피해 받음(플레이어가 몬스터에게)**: 자기 클라 기준 (§14 원칙 그대로)
- **위치·어그로**: **서버 권위** + 추측항법(dead reckoning: 위치+속도 전송, 클라가 이어서 계산) + 보간
- 로컬 권위는 "내 캐릭터 조작감"용일 뿐, 몬스터를 각자에게 맞추는 게 아님 (사용자 명시)
- 어그로 대상 전환: 가장 가까운 대상이 바뀌어도 즉시 안 바꾸고 **0.5초 뒤 전환**(히스테리시스, 튜닝)
- 대상 선정: 각 플레이어가 서버에 보고한 위치로 가장 가까운 놈 → 실제로 가까운 놈 쫓음

### 21-2. 죽음·상태 전환
- **밟은 클라가 확정 → 서버 relay 전파**(멱등). 서버는 검증 없이 중계
- 밟기 손맛: 밟은 사람 화면 즉시 튕김+스쿼시(로컬 0ms)
- 중복 보고(여러 명 밟음)는 멱등 처리

### 21-3. HP 다회 몬스터 (큰 쿠파·부메부메·가시복어 등)
- HP 몬스터는 **실제로 존재함** (초기에 "없다"고 한 것은 오류였음)
- **HP = 숫자 카운터가 아니라 "독립 타격 이벤트의 집합"** (원작 포키 세그먼트 방식).
  각 타격 = 고유 ID 이벤트 → 서버가 집합에 병합(합집합=멱등·순서무관) → 집합 크기 ≥ HP면 죽음.
  숫자 덧셈(경쟁조건)을 집합 합집합(경쟁조건 없음)으로 바꾼 것 → relay와 충돌 없음
- **무적 프레임(i-frame)**: 마리오 표준(피격 후 ~2.5초 무적, 깜빡임). **서버가 지연 고려해 무적
  여부 판정 후 클라에 전파**(클라 로컬로 걸러진다고 한 것은 정정됨). 무적(2.5s) ≫ 지연(0.3~0.5s)
  이라 동시 다중 타격이 사실상 차단됨. 이중카운트는 집합 멱등 + 서버 판정으로 내부 처리

### 21-4. 밟기 반응 유형 (원작 검증)
| 유형 | 처리 |
|---|---|
| 즉사(굼바) | HP 1 |
| 상태전환(부지→껍질) | "죽음" 대신 상태 전환, 껍질은 독립 이동 오브젝트(서버 권위) |
| 세그먼트(포키) | 마디 = 독립 즉사 부위들, 위 마디 처치 시 아래도 |
| HP 다회 | 집합 기반 + 무적 프레임 |
| 밟기 불가(가시돌이) | 밟은 사람 피해(자기 클라), 몬스터 무변화 |
| 트램펄린화(홉챱) | 플레이어만 튕김(로컬) |
| 넉백(불리) | 플레이어만 밀림(로컬) |

## 22. 몬스터 패턴·트리거 (에셋 생성 프리셋)

### 22-1. 프리셋 방식
- 생성 시: **동작 프리셋 1택 + 트리거 프리셋 1택 + 3단 enum**(near/normal/far 등). 정밀 수치 안 정함
- 지형무시는 **패턴에 고정**(유저 선택 아님) — 파이어바는 항상 무시, 굼바는 항상 충돌

### 22-2. 동작 패턴 축 (★=지형무시)
보행/왕복 · 지상추적 · 낙하돌진 · 가로돌진 · 곡선하강추적★(앵그리선) · 포물선도약★(라바버블)
· 순간이동★(마귀공) · 지형통과부유★(부끄부끄) · 제자리회전★(파이어바) · 진자스윙★ ·
반경묶임돌진(체인촘프) · 땅속출현(두더지) · 줄기신축(크리퍼) · 경로왕복★(레일) · 발사(대포·해머브로)

### 22-3. 트리거 축
상시 · 주기 n초 · 접근감지(x축/y축/반경) · 시선(보임/안 보임) · 점프동기화(스킵스퀵) ·
밟힘/타격 · 스위치 ON/OFF · 리듬(보스)

### 22-4. 난이도 (우리 구조 기준)
- **쉬움**(시간 결정론, 로컬 계산 가능): 보행/왕복, 회전, 스윙, 경로왕복, 직진발사
- **중간**(플레이어 위치 의존 → 서버 판정): 낙하돌진, 포물선도약, 지상추적, 곡선하강추적,
  땅속출현, 줄기신축
- **어려움**(네트워크 마찰): 시선반응(누구 시선? 서버가 "한 명이라도 보면 정지" 종합),
  순간이동(불연속→선딜), 반경묶임돌진, 폭발(광역 판정)

### 22-5. 구현 범위 확정
- **어려움 4패턴(순간이동·시선·폭발·반경묶임)도 1차부터 전부 구현.** "자리만 잡아둔다"는 없음(사용자 명시)
- **탑승체(쿠파카·클라운카)도 넣을 수 있음** — "탑승 = 플레이어 컨트롤러가 탈것 컨트롤러로 교체"
  (§25의 Mover 구조에 얹힘). 넣을지는 결정 대상이나 "안 되는 것"은 아님

### 22-6. asset-attributes.md에 아직 없는 축 (편입 필요)
- 취약성 매트릭스(밟기/불꽃/껍질/스타/스핀/내려찍기/폭발 각 O·X) — 지금은 밟기 반응만 있음
- 껍질 메커니즘(밟기→껍질→투척무기→연쇄), 폭발물(밥옴), 출현 트리거, 반경묶임, 줄기신축, 지형무시 플래그

## 23. 선딜(telegraph) — 지연 흡수 마스터 패턴

### 23-1. 원리
- 비결정론적·불연속 액션은 **긴 예비 동작**으로 감쌈
- 선딜 시작 시 **서버가 결과 확정(순간이동 목적지·돌진 방향 등) + 실행 절대 시각 전파**
- 실행 순간 전원 화면에서 동시 발생. 지연이 선딜 안에 흡수됨

### 23-2. 선딜 길이 & 재생 속도 (1초 강제 폐기)
- 길이 = **게임 감각 기준으로 짧게**: 큰 위협(순간이동·폭발·큰 돌진) 0.5~0.8초, 잦은 소동작 0.2~0.3초
- 남는 지연 = **각 클라가 선딜 애니메이션 재생 속도를 조절**해 흡수: 실행 시각까지 여유면 정상~약간
  느리게, 촉박하면 빠르게 압축. 대부분 정상, 지연 심한 소수만 살짝 빠른 선딜을 봄
- 재생 속도가 동기화 노브 → 선딜이 스프라이트 프레임 수에 안 묶임

### 23-3. 적용
- 순간이동: "모임/빛남" 선딜 동안 목적지 확정·전파 → 동시에 사라지고 나타남
- 폭발(밥옴): **도화선 자체가 선딜**(점화→2초→폭발). 범위 피해는 각 플레이어 자기 화면(§14)
- 반경묶임돌진: "으르렁/당김" 선딜 → 방향 확정. 반경 제약은 결정론 로컬 계산
- 낙하돌진(쿵쿵)·도약도 원작이 떨림·웅크림 선딜을 이미 가짐 (예고=공정성)
- **시선 반응만 선딜로 안 풀림**(연속 상태) → 느린 접근 + 정지↔접근 전환 관성(급전환 금지)으로 흡수

## 24. 애니메이션 정책 (우리 게임의 강점)

### 24-1. 전부 AI 스프라이트 애니메이션이 목표
- 코드 연출(깜빡임·떨림 등)은 우리 강점(AI 애니메이션)을 깎으므로 **최소화**.
  코드/1×1 이미지는 **영구가 아니라 최후의 임시 폴백**
- 몸동작은 AI, 순수 이펙트(폭발 섬광·발사체 궤적)도 **궁극적으로 AI 애니메이션**이되 최하위 우선순위

### 24-2. 생성 우선순위 — 절대적
- **어떤 경우에도 상위 순위 대기열이 남아 있으면 다음 순위는 생성 안 됨** (사용자 명시, 절대 규칙)
- 1순위(필수): idle, move
- 2순위(공통 땜빵): 하나로 여러 패턴을 대체하는 공통 선딜/실행 애니메이션
- 최하위(전용): 폭발섬광·발사체궤적 등 전용 이펙트 애니메이션 — 계속 밀려도 됨
- 전용 미완 시 2순위 공통으로 폴백, 완성되면 교체
- 예외: 엉금→껍질처럼 시각이 완전히 다른 상태는 별도 스프라이트(껍질은 독립 오브젝트)
- ⚠️ §20의 "구름 파티클 = 코드 파티클" 방침도 이 정책에 따라 "최하위 우선순위 AI 애니메이션이
  목표, 코드는 임시 폴백"으로 갱신

## 25. 4대 해결책 (원작 검증 완료)

- **탑승 캐리**: 발판 = "움직이는 지형", 위 플레이어가 발판 이동량(delta)을 자기 좌표에 흡수(실제
  위치 변경, rideOffset 연출과 별개). 컨베이어도 동일 — 원작이 "벨트 위 중력 요소는 벨트 방향
  이동"으로 같은 방식 확인됨. 세로 발판이 빨리 하강하면 grounded 해제→분리
- **힘 부여**(범퍼/상승기류/트램펄린/넉백): 오브젝트=서버 위치, 힘 받는 플레이어가 자기 클라
  접촉 판정 후 자기에게 속도 적용(§14). 오브젝트는 "부여할 힘(방향·크기)"을 속성으로 가짐
- **비직선 이동 = Body + Mover 분리**: Mover 종류 LinearPath(리프트)/Orbit(파이어바)/
  Pendulum(스윙)/Charge(돌진). 플레이어 컨트롤러도 Mover의 일종. 결정론 Mover는 로컬, 트리거형은 서버
- **상태별 조작 = modifier 스택**: 거대버섯(크기배율+생명)/가속(속도배율+타이머). 최종능력 =
  기본(tuning) × Π(활성 modifier). 웅크림(속도×0.4)이 이미 이 패턴

## 26. 자기 변형 — 통일 규칙 (§17 보강)

### 26-1. 하나의 규칙
- 자기 변형(스쿼시/찌부/압축)은 **무조건 연출**, 실제 위치·히트박스 절대 불변
- **원인(접촉/막힘)이 지속되는 동안 유지, 원인이 사라지면 원복** — 이 하나의 규칙으로 통일.
  "순간이냐 지속이냐"는 상황이 결정하는 것이지 케이스별 다른 규칙이 아님
  - 밀기: 계속 맞대므로 원인 지속 → 오프셋 유지
  - 천장 점프: 막힘이 순간이면 압축도 순간, 계속 눌려있으면 압축도 유지

- 전 엔티티 공통 속성

### 26-2. 천장 막힌 점프 (신규 사례)
- 상황: 천장이 낮거나 머리에 딱 맞아 점프해도 위로 못 감
- 실제 물리: 히트박스·위치 불변(제자리)
- 연출: 스프라이트 **위쪽으로 압축**(천장에 눌려 공중부양하려는 느낌)
- **점프 소리는 재생**(시도됐으므로)
- 트리거: 점프로 vy<0(상승)인데 머리가 천장에 닿아 vy=0으로 막히는 순간
- 순수 로컬 연출 → 서버·동기화 무관

# ★ 2026-07-12 세션 3차 확정분 (§30~) — 잡기·발사체·§29

## 30. 잡기(carry) 시스템

### 30-1. 기본
- **잡기 넣음.** 잡기 가능 여부는 **에셋 옵션**(유저가 "잡을 수 있음" 선택). **몬스터는 잡기 불가**
  (단 껍질 상태는 예외 — 껍질은 독립 오브젝트)
- 키 = **K**(기본), 나중에 설정에서 키매핑 가능
- 홀드 = 들고 있음, **릴리스 = 발사**(별도 던지기 동작 없음, SMB3식). 위 입력 조합 = 위로 던짐
- 발사 속도 = 기본 던지기 속도 + 플레이어 vx 일부 가산, 방향 = facing
- **잡은 채 모든 행동 가능 — 제약 없음**(이동·점프·웅크리기·내려찍기 전부)
- **던진 직후 잠깐(튜닝) 던진 사람 본인은 그 물체 충돌 무시** (자기가 던진 게 자기한테 맞는 것 방지)

### 30-2. 들고 있는 물체 = 완전 무해
- 들고 있는 동안 물체는 **그냥 이미지**, 아무 상호작용 없음
- **던지거나 놓는 순간에야** 그 물체 옵션대로의 판정 발동

### 30-3. 손 연출 (기본 제공 고정 에셋 + 색 틴트)
- **손 스프라이트 = 게임 기본 제공 고정 에셋 1개** (AI 생성 아님, 유저 제작 아님).
  발사체의 "기본 제공 탄"과 같은 계열이나, 손에는 **캐릭터 색 기반 틴트**를 얹음(손 전용 새 방침)
- 손은 캐릭터 중앙 기준에서 **물체 쪽으로 쭉 뻗은** 모양. 평상시 숨김, 잡을 때만 표시
- **스프링(관성 지연)**: 물체는 캐릭터에 고정(위치 정확)이나 **손 스프라이트만** 캐릭터 움직임을
  살짝 늦게 따라오며 출렁. 순수 로컬 연출, 물체 위치엔 영향 없음
- **스프링은 원작 요소 아님 — 우리 자체 추가** (마리오는 물체를 몸 앞에 딱 고정)
- 던지기/놓기 = 별도 애니메이션 없이 **즉시 손 숨김**

### 30-4. 네트워크 — 확률 기반 소유권 중재 (§14 철학의 정점)
- 각 클라는 **로컬에서 즉시 잡음**(지연 0, 손맛) → **두 클라가 같은 물체를 동시에 잡는 순간이
  실제로 생김**(각자 화면에선 자기가 주인)
- **서버가 진짜 주인 판별**: 여러 잡기 보고가 오면 **도착이 빠를수록 당첨 확률↑, 단 100%는
  아닌 가중 확률**로 결정
  - 이유(사용자): 냉정한 선착순이면 환경 나쁜(고지연) 유저가 항상 져서 슬픔 → 빠를수록
    유리하되 느려도 가끔 이기게
- 진 클라: 잡기 취소 → 물체가 손에서 **사라짐**. **단 취소 전에 이미 한 일(이동·점프·던지기·
  맞춘 것)은 원복 안 함** — 플레이어 위치·행동은 로컬 권위라 §14 그대로. 소유권만 서버가 회수
- 구현: 서버가 잡기 보고를 **짧은 경합 윈도우**(대략 지연 상한) 동안 모아 도착순 가중 확률로
  당첨자 선정 → 전파. 클라는 이미 로컬로 손에 넣었으니 체감 지연 없음
- 피격/죽으면 물체 떨어지거나 발사(서버 권위 복귀)

### 32-2. 진행 중 (미확정)
**5. 블록 파괴 경위** — 정리 중:
- 원래 두 종류 혼재: (a)파괴형 발판(접촉→시간차 낙하/소멸→재생, asset 접촉반응),

  껍질·폭발 도입으로 전제 바뀜 → 재생되면 소프트락 없으니 타격 파괴 재허용 가능
- **확정된 것**: 파괴 대상은 **"파괴 가능으로 지정된 블록만"**(일반 지형 불가). 파괴 트리거는
  **유저가 무슨 수단으로 파괴 가능한지 선택**. **재생 무조건 됨**
- **미해결 1 — 화면구성**: "이 블록이 파괴 가능하고 무슨 수단에 부서지나"를 유저에게 어떻게
  설명·노출할지 (에디터 UI) 미정
- **미해결 2 — 밟기/내려찍기/아래서치기 트리거 타당성**: 사용자가 "밟기·내려찍기·아래서 치기가
  파괴 트리거인 건 좀 이상함"이라 지적. **원작 조사 결과**:
  - 원작 벽돌 블록은 **위에서 걷기·밟기로는 안 부서짐**(그냥 단단한 바닥)
  - **아래서 머리로 치기**(큰 상태) 또는 **위에서 내려찍기**(후기작)로만 부서짐
  - 껍질(옆/아래), 밥옴 폭발로도 부서짐
  - 즉 "그냥 밟기(위에서 서기)"는 원작에서 파괴 트리거가 아님 → 사용자 지적이 맞음.
    **밟기를 파괴 트리거에서 빼는 게 원작 부합**. 아래서 치기/내려찍기/껍질/폭발만
  - → 이 조사 결과 기반으로 파괴 트리거 목록 재확정 필요(다음 논의)

**6. 턱 자동 상승 = 코너 보정(원작 의도 기능, 버그 아님)**:
- 조사 결과: ledge forgiveness / corner correction은 거의 모든 플랫포머의 의도적 관용.
  마리오64도 "다음 스텝이 벽 안이면 벽 위 30~150유닛에서 바닥 찾아 끌어올림"
- 두 방향: 발 코너 보정(발판 모서리 살짝 못 미치면 끌어올림 = 우리가 본 현상),

# ★ 2026-07-12 세션 4차 확정분 (§33~) — A~L 일괄 확정 + 벽타기 마리오식

## 33. 전반 방향 — 마리오 베끼기
- **전반적으로 마리오(SMM2 등)를 베끼는 방향** 확정
- 단 **원작 세부 수치(px·속도·시간)는 대부분 비공개** → "동작 방식(로직)은 베끼되, 수치는
  우리가 튜닝으로 맞춘다". "정확히 베낀다"는 불가, "느낌 재현 + 튜닝"이 방침

## 34. 벽타기 최종 (§15·F 대체) — 마리오식 + 초반 강화
- **낙하속도를 낮은 상한으로 제한(느린 낙하 유지)** = 마리오 벽 슬라이드 방식.
  이전의 "붙는 순간 30% 리셋 + 재가속"은 **폐기**
- **2단계 상한**: 붙는 순간 잠깐은 `wallSlide.grabMaxFall`(더 낮음, 강하게 잡음) →
  전환 시간(튜닝) 후 `wallSlide.maxFall`(낮음, 평상 유지)로 완화
- 발동: 벽 접촉 + 벽 쪽 입력 홀드. 벽 반대/무입력도 유예시간(~120ms) 유지(벽 클링 코요테)
- 마리오 조사: 벽 슬라이드는 3D(선샤인+)의 것. 2D 클래식은 글리치성. NSMB 세부 수치 비공개.
  "벽 쪽 홀드 시 느린 낙하"가 핵심 → 그 로직 채택 + 초반 강화만 우리 감각으로 추가

## 35. A~L 확정

# ★ 2026-07-12 세션 6차 (§40~) — 카테고리 통합 + 블록(part) 확정

## 40. 카테고리 재편 + 용어
- **플랫폼 + 장애물 = 하나로 통합** (경계 모호: 트램펄린=플랫폼+튕김, 가시=장애물+고체.

- 최종 카테고리: **블록(part) / 몬스터 / 아이템 / 배경 / 아바타**

  연동 블록=서버 상태 받아 로컬 반영(§35-I 패턴)

- 반응 선택 시 **기준 상태 [ON일 때 / OFF일 때]** 라디오 — 이게 초기 상태 겸 편 가르기
  (원작 빨강/파랑 점선 블록 = 두 블록을 반대 기준으로)

### 44-1. 세부 확정
- **충돌 "통과"**: 파이어바처럼 고체 아님(닿아도 안 막히고 효과만)
- **접촉 효과 + 이동 동시 허용**(쿵쿵 재현. 예전 "동시 금지" 권고 해제 — 서버 권위라 감당)
- **미는 블록(유저가 밈)**: 위치 무조건 **서버 권위**. 대신 미는 순간 **짜부 연출(자기변형)로
  "밀리는 블록 + 밀리는 힘 받음"을 클라 즉각 표시**(§14 원칙: 손맛=즉시 연출, 실제=서버 확정)
- **파괴 "밟기 제외 / 내려찍기 포함"**: 밟기=위에서 딛고 서기(안 부서짐), 내려찍기=공중 ↓
  내리꽂기(부서짐). 둘은 다른 동작이라 모순 없음
- **시소**: 서버 권위·예측 없음, 중심축=엔티티 중앙 고정, 1×1 가능

### 44-2. 이동(Mover) 에디터 구현
- 경로왕복: "이동" 켜면 경로 편집 모드 → waypoint 순서 클릭(**직선 구간만**: 수평/수직/대각)
  → 선 연결. 속도 프리셋, 왕복/순환
- 밟으면시작/침몰: 시작점+방향(+거리). 회전/진자: 중심·반경·속도 프리셋.
  감지시돌진: 방향+복귀/재생성/일회성. 시소: 토글+최대기울기
- LLM 채팅: "왼쪽 3칸 왕복 발판" → 자동 경로 생성

# ★ 2026-07-12 세션 7차 (§45~) — 재생성 통합·라인 격리·탑승체 제거·AI 파이프라인 현황

## 45. 소멸→재생성 통합 규칙 (전역)
- 모든 것(몬스터·블록·물체 등)이 소멸/사라지면 **7.5초 뒤 원래 자리에 재생성**
- 재생성 시 **페이드인**, 페이드인 동안 **상호작용 불가**(디버프)
- 소멸 = **페이드아웃**(§46). 페이드아웃/페이드인이 짝
- 기존 파괴블록 5초·집기재생 10초 → **전부 7.5초로 통합**
- 재생 위치에 엔티티 있으면: 겹친 대상 밀어냄(MTV), 밀 데 없으면 가장 가까운 빈 곳으로

## 46. 라인 경계 = 활동 경계 (전역)
- **모든 활동체는 자기 라인(세그먼트) 안에서만 활동.** 라인 경계 넘으면 **무조건 페이드아웃**
- 페이드아웃 = **순수 연출** — 시작 즉시 실제로는 **소멸**(손에 든 것 없어짐, 상호작용 사라짐).
  페이드는 눈에만 보이는 잔상
- 대상: 잡은 물체 / 발사체 / 몬스터 등 "위치 갖고 돌아다니는 활동체"
- **플레이어 본체는 예외** (레이스라 라인 넘어 계속 달림). 사라지는 건 "가진 것·생성한 것"만
- **몬스터가 라인 밖 = 페이드아웃 = 사망 판정** → §45로 7.5초 뒤 원위치 재생성
- 함의: 발사체·든 물체 라인 넘으면 소멸(타 라인 공격/반출 불가)

## 47. 스위치 — 전역 → 라인 격리로 정정 (§42 수정)
- **§42의 "전역 스위치"는 폐기.** 스위치는 **생성된 라인(세그먼트)에서만 적용**
- 집기 가능한 스위치가 다른 라인으로 옮겨져도 **영향은 원래 생성 라인에만**
- 즉 스위치도 §46 라인 격리 원칙에 포함(신호도 라인 스코프)
- 권위: 상태=서버 권위(해당 라인 내 일치), 누름=로컬 즉시+relay는 유지

## 48. 탑승체 — 완전 제거 (확정)

# ★ 2026-07-12 세션 8차 (§50~) — 조건·행동 시스템, 발사체, 레지스트리 구조, 파츠=축 조합, 공용 이펙트

## 50. 용어 확정 (재정정)
- **파츠(Part)** = 유저가 만드는 **모든 것**의 상위 통칭 (블록·몬스터·아이템·배경·아바타 전부)
- **블록** = 파츠의 한 종류(플랫폼+장애물 통합). 코드 폴더 = `shared/parts/`
- 이전에 "엔티티"라 부른 상위 개념 = 파츠

## 51. 몬스터 = "조건 → 행동" 규칙의 집합
- 몬스터는 `[조건] → [행동]` 규칙을 **여러 개** 가짐. 매 틱 조건 평가 → 참인 규칙 행동 실행
- **같은 우선순위 규칙 여러 개 참이면 랜덤** 선택. 우선순위 다르면 높은 것
- 이건 행동 트리의 단순형. 유저가 자유롭게 몬스터 AI 조립
- **구조 = 몬스터 두뇌(트리거 시스템) + 몸(물리엔진), controller로 분리** (stepPlayer와 대칭:
  stepPlayer는 키입력을, stepMonster는 규칙을 명령으로 변환. moveAndCollide는 둘 다 받음)
- **규율**: 모든 조건은 물리 상태(또는 근사)로 표현 가능해야 함. 물리에 없는 개념(시야)은
  facing+거리로 근사

## 52. 조건(Condition) 목록
| 갈래 | 조건 | 파라미터 |
|---|---|---|
| A. 시간 | 상시 / 주기(n초) | 짧게·보통·길게 |
| B. 감지 | 근접(반경/x축/y축) / 방향(상하좌우) / 시야(봄·안봄) | near·normal·far |
| C. 행동 | 플레이어 점프 시 | — |
| D. 자신 상태(취약성 연결) | 밟힘 / 피격 / 체력 n 이하 / 착지 / 행동 완료 | — |
| E. 환경 | 절벽 앞 / 벽 접촉 / 스위치 ON·OFF | — |
| 조합 | AND / OR / NOT (조건 트리) | — |
- **복합조건(AND/OR/NOT)** 지원. 파라미터는 3층(3단 프리셋 + 고급 슬라이더 + LLM 자연어)
- D는 취약성이 판정(밟기=죽음/무효/상태전환) → 상태전환이 조건 규칙을 깨움. 취약성↔조건 연결
- 감지 3종(근접/방향/시야)으로 시작, **플러그인식으로 확장 가능**

## 53. 행동(Action) 목록 — 마리오 베끼기
- **이동**: 정지 / 걷기 / 왕복 / 추적 / 도주 / 비행·부유 / 벽·천장 기어가기 / 도약 / 포물선 부유
- **능동 공격**: 낙하돌진 / 가로돌진 / 순간이동 / 발사 / 잠복→출현 / 신축 / 회전
- **상태 전환**: 분노 / 기절 / 껍질화(독립 오브젝트) / 분열 / 부활
- **상호작용 부여**: 넉백 부여 / 튕김 부여(트램펄린화)
- 각 행동 = Body에 속도·힘 쓰기(= 몬스터의 "입력"). 회전·잠복·신축 등 특이 행동도 1차 포함
- 마리오에서 안 뺌(물·탑승 제외는 이미 됨)

## 54. 발사체 — 파츠 공통 축 재사용 (원작 검증)
원작 확인: 실탄형(불릿빌·캐논볼·유도미사일) = **밟으면 처치 + 밟고 오르기**. 에너지형(불꽃·
마법탄) = **밟기 불가 + 지형 닿으면 소멸**. 밥옴 = 잡아 되던지기.
→ 발사체도 종류별 상호작용이 달라서, **파츠 공통 축을 골라 조합**한다.

**발사체 고유 축(움직임)**:
- 궤적 [배타]: 직선 / 포물선(중력) / 유도
- 발사 방향 [배타, 직선·포물선]: 고정(좌우상하대각) / 발사 순간 플레이어 겨냥 / facing
- 속도(느림·보통·빠름, 전역 상한 §41) / 회전(진행방향 정렬·코드회전) / 수명(시간·거리·벽충돌) /
  관통 T/F / 지형충돌 시(소멸·튕김)

**파츠 공통 축 재사용**: 접촉 효과(피해·즉사·넉백·튕김·스위치토글) / 밟기 반응(처치·불가·오르기) /
잡기 가능 T/F / 취약성

**네트워크**: 직선·포물선·겨냥(발사시점만 relay) = 결정론 로컬. **유도만 서버 권위**(비결정론).
유도는 서버 지연 + 의도적 약한 유도(homingStrength 튜닝)로 회피 가능 = 지연이 밸런스 장치.
**라인 격리(§46)** 적용. 잡아 던진 껍질·밥옴도 발사체 구조 공유.

## 55. ★ 파츠 = 공통 축의 조합 (상위 설계)
- 블록·몬스터·발사체를 **따로 옵션 표로 짜지 않는다.** 모든 파츠가 **공통 축 풀에서 필요한 걸
  골라 조합**하는 것:
  - 블록 = 크기+충돌+접촉효과+이동(Mover)+물성+...
  - 몬스터 = 크기+이동+접촉효과+조건·행동+취약성+...
  - 발사체 = 크기+궤적이동+접촉효과+밟기+잡기+수명+...
- **축(접촉효과·잡기·밟기·이동·취약성...) = 공통 풀에 하나씩. 파츠 종류마다 "쓸 수 있는 축"만
  다름.** 다음 작업: 공통 축 풀 정식 정리(각 축이 어느 파츠에 쓰이나)

## 56. 레지스트리 디렉토리 구조 (§1 갱신)
"옵션 하나 = 파일 하나 + 등록 한 줄. 기존 코드 무수정"을 위한 레지스트리 패턴.
```
shared/
├── physics/          순수 엔진 (파츠·옵션 모름): body.ts(Body+moveAndCollide,MTV),
│                     terrain.ts, tuning.ts, index.ts
├── behavior/         조건·행동 시스템
│   ├── types.ts        Condition, Action, Rule, Context
│   ├── registry.ts     이름→함수 등록·조회
│   ├── evaluate.ts     stepRules (매 틱 평가·랜덤선택)
│   ├── conditions/     ★ 조건 1개 = 파일 1개 (playerWithin.ts, inSight.ts, onStomped.ts...)
│   │   └── index.ts    (전부 import → 자동 등록)
│   └── actions/        ★ 행동 1개 = 파일 1개 (walk.ts, slamDown.ts, shoot.ts, enrage.ts...)
├── properties/       ★ 블록 물성 1개 = 파일 1개 (conveyor.ts, trampoline.ts, ice.ts, seesaw.ts...)
├── effects/          ★ 공용 이펙트 1개 = 파일 1개 (§57)
├── parts/            ★ 파츠 = 유저가 만드는 모든 것
│   ├── block.ts        Body + properties + behavior 조합
│   ├── monster.ts      Body + behavior 규칙
│   ├── projectile.ts   Body + 궤적 + 공통 축
│   ├── item.ts, background.ts, avatar.ts
│   └── ...
└── maps/
```
- 각 조건·행동·물성·이펙트 파일이 `register___()`로 중앙 레지스트리에 자기 등록
- 유저 JSON `{"type":"playerWithin",...}` → 레지스트리 조회 → 함수. 런타임이 해석
- **물리엔진은 조건·행동·물성을 모름** — Body에 명령 써지면 계산만. 옵션과 엔진이 독립 발전

## 57. 공용 이펙트 (effects/) — 재사용 풀
- 이펙트를 파츠마다 따로 안 만들고 **재사용 공용 세트**. 이름으로 호출: `playEffect("stun", pos)`
- 성격: 순수 연출(로컬, 네트워크 무관). §37-1 기준상 대부분 **코드 또는 최하위 우선순위 AI**
  (발사체 이미지 방침과 동류). 필요시 대상 색 틴트
- 초기 목록: **먼지 구름**(달리기·벽타기·착지 접점) / **폭발**(섬광+파편) / **피격**(번쩍임·별) /
  **기절**(머리 위 도는 별·새) / **처치**(펑/뿅) / **스폰 반짝임**(§45 페이드인에 얹음) /
  점프·착지 먼지(선택)

# ★ 2026-07-12 세션 9차 (§58~) — 아이템·크기·배경·라인 규격·에셋 참조·매핑

## 58. 아이템 — 재정의 (기존 거대버섯/가속/스타 3종 폐기)

| 종류 | 효과 |
|---|---|
| 가속 | 이동속도 배율, 시간제(튜닝) |
| 크기 증가 | 크기 단계 +1 |
| 크기 감소 | 크기 단계 −1 |
| 생명력 +1 | 생명 +1, **최대 2** |
| 무적 | 시간제. 몬스터 접촉 즉사, **PvP는 접촉 넉백만**(즉사 X) |
| 점수 아이템 | 점수 부여. **라인별 배치 개수 상한** |

- 획득 = 접촉 즉시, 자기 클라 판정(§14). **획득 경합은 서버 가중랜덤 중재**(잡기와 동일, §60)
- **획득 연출: 0.4초(튜닝) 위치 고정 + 무엇에도 안 밀림 + 하이라이트.** 크기 전환도 이때 처리
- **효과 종료 옵션**: `지속시간(T/F+값)` + `피해 시 제거(T/F)`. 피해 시 제거 OFF면
  **낙사로 죽어도 효과 유지**(부활 후에도). **라인 이탈 시엔 무조건 전부 소멸**(§46 확장)
- 아이템 자체는 §45(7.5초 재생)·§46(라인 격리) 적용
- 점수 시스템 세부(순위와 관계)는 게임 흐름 때 — 나중

## 59. 크기 단계 시스템

| 단계 | 크기 |
|---|---|
| 1 (감소) | **1×1** (가로1×세로1타일) |
| 2 (기본) | 1×2 규격 — 히트박스는 그림 따라 1.3~1.95 자동 |
| 3 (증가) | 기본 대비 **가로 2배 × 세로 1.5배** |

- 아바타: 크기 아이템은 **자동 산출 히트박스에 단계 배율 적용**(3단계 = 자동값 × 가로2·세로1.5),
  1단계는 1×1로 덮어씀
- **웅크리기 = 크기 단계 무관 키 1칸 고정**(히트박스 0.95타일) — 3단계여도 웅크리면 1타일 틈 통과.
  원작과 다름(우리 1×2 체계 맞춤)
- **크기 증가 시 낑김**: 세로는 강제 웅크림으로 해소, **가로는 그냥 MTV로 밀려나는 느낌**
  (별도 예외 없음, 기존 겹침 해소 재사용). 성장 겹침은 압사 판정 예외

## 60. 서버 권위 — 일반 원칙 + 신규 2건
> **"결과가 하나여야 하는 비결정론(랜덤·경합·소유)은 전부 서버가 확정한다."**
- 신규 1: **랜덤 결과 전반** — 물음표 랜덤 내용물, 몬스터 동순위 규칙 랜덤 선택 등
  모든 랜덤은 서버가 굴려 결과 전파 (클라마다 다른 세계 방지)
- 신규 2: **아이템 획득 경합** — 두 명 동시 획득 시 잡기 소유권과 동일한 가중랜덤 중재 재사용
- 기존 사례 인벤토리: 시소 / 유도탄 / 몬스터 위치·어그로 / 스위치 상태 / 잡기 소유권 /
  무적프레임 / 선딜 절대시각 / 미는 블록

## 61. 에셋 참조 시스템 (옵션 값 = 다른 에셋)
- **"옵션 값으로 내 것/DB의 다른 에셋을 참조"** — 일반 개념
- **물음표 내용물**: 에셋 1개 또는 **여러 개 + 랜덤**(랜덤 결과는 서버 확정 §60)
- **발사체 발사 파츠의 탄**: 같은 방식(에셋 참조)
- 허용 범위: **배경·아바타 제외 전부**(몬스터 포함 — SMM2도 물음표에 적 넣기 가능, 함정 재현)

## 62. 배경 — 재정의
- **크기 고정**(유저가 못 정함, 규격 상수)
- 가로 반복: **좌우반전하며 연결할지 T/F**
- 세로: **상하반전 연결 / 끝부분 연장(가장자리 늘이기)** 택1
- 충돌·상호작용 없음, z 뒤. 정지 1장

## 63. 라인 규격 — 깃발 기반 유동 (확정)
- 라인 = **시작 깃발 ~ 골 깃발**. 에디터에서 깃발 위치로 유동 결정
- **깃발은 x·y 모두 자유 배치** — "올라간 채 끝나는 라인" 허용. 이유: 같은 높이 강제면
  올라가면 반드시 내려와야 하는 맵만 나옴(지형 다양성 박탈)
- **병합 = 시스템이 자동 이음**: 각 라인을 (이전 골 깃발 − 이번 시작 깃발)만큼 평행이동 배치
  → 전체 맵 세로 범위가 조합 따라 유동
- **이음새 = (가) 확정**: 시작/골 깃발 주변 몇 타일은 **시스템 표준 지형(평평한 발판) 강제**
  — 어떤 조합이든 이음새 보장
- 낙사선·카메라도 라인 오프셋 추종
- 라인 경계(격리 §46·스위치 §47·아이템 상한 §58) = 깃발 기준

## 64. 애니메이션·사운드 자동 매핑 — 슬롯 선언 방식
- **각 옵션(행동·물성·상태)이 레지스트리 등록 시 필요한 애니 슬롯·사운드 슬롯을 함께 선언**:
```typescript
registerAction("slamDown", {
  step: ...,
  anim:  { windup: "windup.slam", active: "fall.slam" },   // 폴백 체인 명시 가능
  sound: { start: "slam_start",  impact: "slam_hit" },
});
```
- 파츠 저장 시 → 선택된 옵션들의 **요구 슬롯 합집합** 자동 산출 → 생성 큐 등록
- 슬롯 명명: `idle` / `move` / `windup.행동명` / `active.행동명` / `hit` / `death` / `stun` …
- **우선순위 자동 부여**(§24): 1순위 idle·move → 2순위 공통 슬롯(windup.generic 등) → 최하위 전용
- **폴백 체인**: `windup.slam` → `windup.generic` → 코드 연출(임시)
- **사운드 동일 구조**, 단 AI 생성 아님 — **기본 제공 사운드 풀에서 매핑**
  (점프/착지/밟기/피격/획득/스위치/파괴/발사…)
- 확장성: 새 행동 파일 하나에 물리+애니+사운드 요구가 같이 선언 → 생성 파이프라인은
  "파츠의 요구 슬롯 목록"만 읽음. 슬롯 이름으로만 통신
- **아바타 요구 슬롯 고정**: idle / walk / onair / spin

## 65. behavior 통합 — 최종 확정
- 블록 Mover도 조건→행동의 특수 케이스로 **통합 확정** (블록 왕복 = [상시]→왕복 등)
- 반례 점검 결과 시소만 애매 → 시소는 어차피 서버 권위 특수 처리라 예외
- ⚠️ 사용자 경고 기록: 서버 권위 특수사례를 놓쳤을 수 있음 — 새 기능마다 §60 원칙
  ("결과가 하나여야 하는 비결정론인가?")으로 점검할 것

## 66. 아바타 키(높이) — 이산 스냅으로 변경 (2026-07-13)
- **기존**: 그림에서 산출한 세로 비율을 **1.35~1.95타일 연속 범위로 clamp**하려 했음.
- **변경 확정**: 산출 높이를 **{1.1, 1.3, 1.5}타일 중 가장 가까운 값으로 스냅**(3단계 이산).
  - 예: 1.42→1.5 / 1.18→1.1 / 1.25→1.3. 최대 1.5타일.
- **적용 위치**: 그림→히트박스 높이 산출 단계(아바타 생성 파이프라인). 현재 테스트맵은
  파이프라인 미구현이라 고정 높이(`sizes.playerHeight`) 사용 — 파이프라인 붙일 때 스냅 헬퍼 구현.
- 가로(폭)는 기존대로 1타일 기준(§59), 크기단계(§59)는 이 base 높이에 배율.
