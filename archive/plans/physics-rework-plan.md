# 물리·룸 구조 재작업 계획 (정리본, 미구현)

작성 시점 기준 커밋: `640ee96` (baseworld 서버권위 물리 샌드박스 + 개발자 콘솔).
이 문서는 공유용이 아니라, 논의로 확정된 내용을 한 번에 몰아 구현하기 전 잊지 않기 위한 메모.

---

## 1. 즉시 반영할 플레이어 물리 수정

### 1-1. 트리플 점프 삭제
- 제거 대상: `tuning.json`의 `tripleJump` 블록, `types.ts`의 `jumpChain`/`chainLeftMs`/`wasAirborne`,
  `step.ts`의 점프 배수 계산부(`chainOk`, `p.jumpChain` 순환식), `updateChainWindow`의 트리플 관련 부분만
  (스핀 쿨타임 리셋·내려찍기 점프 유예는 `updateChainWindow`에 남겨야 함 — 분리 필요)

### 1-2. 벽점프 시 스핀 쿨타임 리셋 (버그 수정)
- 원작 확인: 벽점프는 "새 점프 동작"이라 스핀이 다시 허용됨 (오디세이: "스핀 점프를 벽점프로 연결 가능")
- 현재 `spinUsed`는 착지해야만 리셋됨 → 벽점프 순간에도 `p.spinUsed = false` 추가 필요
- 위치: `step.ts`의 벽점프 처리부 (jumpPressed && airborne && touchingWall)

### 1-3. 스핀 시각효과 단순화
- 현재: `scaleX` 좌우 뒤집기(가로 스케일 왕복)로 세로축 회전 흉내
- 변경: 회전/스케일 변형 제거, **색상만 변경**(스핀 중임을 표시)
- 위치: `BaseWorldScene.ts`의 `render()` — `yaw` 계산 및 `scaleX` 적용 라인 제거, `fillColor` 분기에 스핀 케이스 추가
- 내려찍기 hang의 평면 회전(앞구르기)은 원작 일치이므로 유지

### 1-4. 내려찍기 최소 높이
- 목적: 착지 직후 살짝 뜬 상태로 내려찍기 남발 방지
- 방식: "grounded가 false로 바뀐 순간의 y좌표"를 저장 → 내려찍기 발동 조건에
  `Math.abs(p.y - p.airborneStartY) >= t.pound.minHeightPx` 추가
- 필요한 것: `PlayerPhys`에 `airborneStartY: number` 필드 1개 추가, `integrate()` 또는 진입 지점에서
  grounded true→false 전이 시점에 기록
- `tuning.json`에 `pound.minHeightPx` 추가

### 1-5. 경사 슬라이딩 "첫 속도가 느림" 문제
- 원인 확인됨: 내려찍기는 낙하 중 매 틱 `p.vx = 0` 강제 → 경사 착지로 슬라이딩 전환되는 순간 vx=0에서
  다시 가속(3200px/s²)해야 해서 시작이 굼뜸
- 대비: 달리다 웅크려서 슬라이딩 전환(`crouchMinSpeed=240` 이상)하는 경로는 기존 vx를 이어받아 문제 없음
- 원작(NSMB Wii) 대조: 슬라이딩은 상한 없이 경사를 넘나들며 계속 가속(4.07→4.15→4.3배속 언급) —
  우리는 `slide.maxSpeed` 상한이 있어 원작보다 단순화된 상태. 상한을 없앨지는 밸런스 결정 필요(보류)
- 결정 필요: 내려찍기 착지 시 vx=0 강제를 유지할지(스펙 "발동 즉시 좌우 가속 무조건 0"과 상충 가능성 있음),
  아니면 착지 순간에 한해 경사 방향으로 소량의 초기 속도를 부여할지

## 2. 발견된 버그

### 2-1. 밀기(resolvePush)가 지형을 무시하고 벽 안으로 밀어넣음
- 원인: `pvp.ts`의 `resolvePush()`는 플레이어끼리 겹침만 보고 좌표를 직접 수정 (`a.x -=`, `b.x +=`),
  그 결과가 지형과 겹치는지는 전혀 재검사하지 않음
- 지형 충돌은 오직 `step.ts`의 `integrate()` 안에서만 일어나는데, PvP는 그 이후 별도 단계(TestRoom.fixedTick)
  라서 지형을 모름 — "PvP는 지형을 모른다"는 설계 자체가 원인
- 수정 방향 후보:
  (a) `resolvePush`가 terrain을 받아 밀림 결과가 벽과 겹치면 밀림량 축소
  (b) PvP 단계 이후 지형 재클램프 패스 추가
- → 지형 충돌을 `step.ts` 밖으로 꺼내는 범용화(§3)와 맞물린 문제. 범용화 시 자연히 같이 풀릴 가능성 높음

## 3. 범용 물리 아키텍처 — 왜 지금 구조가 안 되는가

### 3-1. 현재 문제
- `PlayerPhys`/`step.ts`가 "지형 충돌(범용이어야 함)"과 "플레이어 능력(전용이어야 함)"을 한 파일에 뒤섞음
- 움직이는 발판을 다루지 못함 — 발판 위 탑승자가 발판 이동량만큼 같이 옮겨지는 처리 없음
- 엔티티-엔티티 상호작용이 일반화 안 됨 — `pvp.ts`는 "플레이어 대 플레이어"만 앎.
  적/아이템/투사체별로 다른 충돌 반응(피해/처치/습득/파괴)을 표현할 태그·레이어 체계 없음
- 지형 조회가 배열 전체 순회(`for (const s of terrain.solids)`) — 엔티티 수 × 지형 수로 느려짐,
  나중에 유저 맵 세그먼트 병합 시 지형 수백 개가 될 수 있어 공간 분할 필요

### 3-2. 참고 자료 확보
- `archive/reference/arcade-physics/` — Phaser Arcade Physics를 Phaser 없이 뗀 TypeScript 패키지
  (yandeu/arcade-physics, MIT/LGPL, 마지막 배포 2023-01, 유지보수 사실상 중단)
- 참고할 구조: `Body.ts`(엔티티 물리 상태), `World.ts`(전체 관리+스텝),
  `SeparateX/Y.ts` + `ProcessX/Y.ts`(축분리 충돌을 별도 함수로 분리 — 우리 `integrate()`가 한 함수에
  다 몰아넣은 것과 대조), `structs/RTree.ts`(공간 분할 — 지형 조회 성능 문제의 해법 참고),
  `StaticBody.ts`(정적/동적 바디 구분 — 발판 이동 문제 참고)
- 한계: Group 미지원(배열로 직접 관리), **타일맵/경사 미지원** — 우리 경사 충돌은 이 패키지로 대체 불가.
  채택 여부와 무관하게 "설계 참고용"으로만 사용

### 3-3. 제안하는 4계층 구조 (미확정, 방향성 논의만 됨)
```
1) 지형 조회 계층   — solids/slopes 공간 분할(그리드/쿼드트리), "근처에 뭐가 있나" 질의
2) 범용 바디 계층    — 모든 엔티티(플레이어/적/발판/투사체) 공통: 위치·속도·중력유무·태그.
                       발판 = "움직이는 solid", 탑승 엔티티는 발판의 틱당 delta를 흡수
3) 종류별 반응 계층  — 태그 조합(플레이어vs적, 플레이어vs발판, 투사체vs적)별 반응 규칙 테이블.
                       pvp.ts는 이 계층의 "플레이어vs플레이어" 규칙 하나가 됨
4) 능력 계층        — 내려찍기·스핀·웅크리기 등 플레이어 전용 상태머신 (지금의 step.ts 대부분)
```
- 규모가 커서 "지금 당장 전부" vs "baseworld 마무리 후 별도 작업"인지 미결정
- 사용자 판단: "처음부터 전부 다 짜야겠네" — 전면 재작업 방향에 동의한 상태 (2026-07-11 대화)

### 3-4. 낑김방지(웅크리기 강제 유지)의 문제점 — 재설계 시 같이 정리
- 현재 위치: `step.ts`의 `standingOk()` + 웅크리기 처리부, 슬라이딩 상태머신 안 2곳
- 문제 1: 지형 충돌 판정 경로가 `integrate()`와 `standingOk()` 두 곳에 중복 구현됨
- 문제 2: `standingOk()`가 `terrain.solids`만 검사, `terrain.slopes`는 검사 안 함 → 경사 밑
  낮은 공간에서 낑김방지가 안 걸리는 숨은 버그
- 제안: 범용 바디 계층에 "이 높이로 여기 놓일 수 있는가" 쿼리 함수를 하나 두고 낑김방지·서기 판정·
  스폰 판정 등에서 재사용 (§3-3의 계층 1·2가 정리되면 자연히 해소됨)

## 4. Room 구조 일반화

### 4-1. 문제
- `TestRoom.ts`(baseworld)가 "물리 시뮬레이션 + 입력 처리 + 상태 동기화 + 개발용 tp/tune 명령"을
  한 클래스에 몰아넣은 baseworld 전용 구현
- 향후 필요한 방 종류:
  | 방 | 특징 |
  |---|---|
  | 로비/대기실 | 플레이어 목록 표시, PvP/생명 로직 없음, 걷기 정도만 |
  | 실제 게임(레이스) | 유저 맵 세그먼트 병합, 생명/부활/완주 판정, PvP 전부 |
  | 맵 에디터 테스트 | 세그먼트 1개 단독 로드, maxClients=1, 즉시 리스폰 |
  | baseworld(현재) | 규칙 없는 순수 물리 샌드박스, 개발용으로 계속 존치 |

### 4-2. 제안 구조
```
server/src/rooms/
  base/PhysicsRoom.ts     ← 추상 베이스: 고정틱 루프, 입력 큐, phys Map, 동기화 3단계
                             (지금 TestRoom.fixedTick의 1)(2)(3)이 여기로 이동)
  LobbyRoom.ts            ← PhysicsRoom 상속, PvP/생명 비활성, 지형=로비 전용 맵
  RaceRoom.ts             ← PhysicsRoom 상속, 생명·부활·완주 판정 추가, 지형=병합 세그먼트
  MapTestRoom.ts          ← PhysicsRoom 상속, maxClients=1, 지형=에디터가 넘긴 세그먼트
  TestRoom.ts (baseworld) ← 유지
```
- 미결정: tp/tune 같은 개발자 명령을 `PhysicsRoom` 공통으로 둘지, baseworld 전용으로 남길지
  (운영 환경에서 일반 유저가 tune을 칠 수 있으면 안 됨 — 권한 체크 또는 방 종류별 분리 필요)

## 5. 테스트 인프라

### 5-1. 문제
- 플레이어 간 충돌(밀기/밟기)을 테스트하려면 2명을 동시에 조작해야 하는데 혼자서는 불가능
- 로컬뿐 아니라 서버가 분리된 환경(원격)에서도 동일하게 되어야 함

### 5-2. 채택 방향 — 두 가지 병행
**A) 물리 유닛 테스트 (우선순위 높음)**
- `stepPlayer`/`resolvePush`/`resolveStomps`는 순수 함수라 브라우저·서버 없이 직접 호출 가능
- 합성한 `PlayerPhys` 2개로 겹침·밀림·벽클립 등을 자동 검증 → 2-1 벽클립 버그의 회귀 방지에 즉시 사용 가능
- 서버 분리 여부와 무관 (네트워크 자체가 필요 없음)

**B) 클라이언트 내장 매크로 (설계 완료, 미구현)** — §6 참조

### 5-3. (참고, 우선순위 낮음) 스크립트 봇 클라이언트
- `@colyseus/sdk`로 접속하는 별도 Node 스크립트, 미리 정한 입력을 자동 전송
- 서버 위치와 무관하게 동작(그냥 평범한 클라이언트 하나 더) — 실제 네트워크 지연까지 재현하고 싶을 때 사용
- 매크로(B)로 상당 부분 대체 가능해서 우선순위 낮춤

## 6. 개발자 콘솔 — 매크로 명령 (설계 완료, 미구현)

### 6-1. 명령어
| 명령 | 의미 |
|---|---|
| `macro record` | 녹화 시작. **길이 제한 없음** — `macro stop`까지 매 틱 실제 키 입력 기록 |
| `macro stop` | 녹화 중 → 녹화 종료(버퍼 확정, 재생 대기). 재생 중 → 재생 중단, 실키 입력 복귀(버퍼 유지) |
| `macro play reset` | 반복마다 **녹화 시작 지점으로 순간이동** 후 재생 |
| `macro play loop` | 위치 리셋 없이 **입력만** 계속 반복 (물리 결과대로 위치가 흘러감) |
| `macro status` | idle / recording(경과 틱) / playing(모드, 진행률) |

### 6-2. 상태 머신
```
idle ──(macro record)──▶ recording ──(macro stop)──▶ idle(버퍼 보유)
                                                          │
                                            (macro play reset|loop)
                                                          ▼
                                                       playing ──(macro stop)──▶ idle(버퍼 유지)
```

### 6-3. 구현 요점
- 데이터: `interface MacroFrame { left; right; jump; down; run: boolean }` (tick 필드 없음, 재생 시 새로 매김)
- 녹화: `BaseWorldScene.fixedTick()`에서 실제 키 입력을 만드는 지점에 옵저버로 얹음
  (`room.send`/`stepPlayer`는 입력 출처를 구분하지 않으므로 무변경)
- `reset` 모드: 버퍼 끝에서 `this.self = createPlayerPhys(macroStartX, macroStartY)`로 능력상태까지 전부 초기화
  + `room.send("tp", {x, y})`로 **서버 권위도 동기화** (기존 tp 핸들러 재사용, 서버 코드 추가 불필요)
- `loop` 모드: 인덱스만 `% buffer.length` 순환, 위치 보정 없음
- 노출 경로: `boot.ts`에 `startMacroRecord()`/`stopMacro()`/`macroStatus()`를 `setServerView`와 같은 패턴으로 추가,
  `commands.ts`에 `macro` 서브명령 추가
- 서버 변경 불필요, 로컬/원격 서버 무관 동일 동작 (클라이언트 내부 입력 생성 트릭이라)
- 경계조건: 녹화 중 `macro stop`은 그 시점까지 기록분 확정(취소 아님, 5초 캡 삭제로 재설계됨).
  재생 중 `macro record`는 기존 재생 즉시 중단 후 새 녹화 시작. join/leave 시 씬 인스턴스와 함께 자동 초기화

## 7. 착수 순서 (제안, 확정 아님)

사용자가 "구현은 한번에 할 것"이라 명시 — 아래는 순서 제안이며 실제 착수는 별도 승인 시점에 결정.

1. §1(플레이어 물리 수정 5건) — 범위 작고 기존 구조 내에서 완결
2. §2(밀기 벽클립 버그) — §3 범용화와 함께 처리하는 것이 자연스러움
3. §5-2-A(물리 유닛 테스트) — 이후 모든 리팩터링의 회귀 방지망으로 먼저 깔아두는 것을 권장
4. §3(범용 물리 아키텍처) — 규모 최대, 발판/적/투사체 도입 시점과 맞물려 결정
5. §4(Room 구조 일반화) — §3과 독립적으로도 착수 가능하나, §3의 엔티티 모델이 정해지면 방 쪽 설계도 영향받음
6. §6(매크로) — §5-2-A와 별개로 언제든 추가 가능, 상호작용 시각 테스트용
