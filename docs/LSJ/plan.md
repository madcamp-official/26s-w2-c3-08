# Multiplayer AI Relay Map Maker MVP 계획서

## 1. 프로젝트 개요

`Multiplayer AI Relay Map Maker`는 사용자가 AI로 생성한 아바타와 에셋을 활용해 각자 짧은 2D 플랫폼 맵 조각을 만들고, 직접 클리어 가능성을 검증한 뒤, 검증된 맵 조각들을 하나의 긴 레이싱 맵으로 병합하여 경쟁하는 웹 기반 멀티플레이 게임 서비스이다. 이 서비스의 핵심 재미는 단순히 주어진 맵을 달리는 것이 아니라, 플레이어가 직접 만든 구간이 최종 레이스의 일부가 된다는 점에 있다. 즉, 제작과 플레이가 분리된 기능이 아니라 하나의 게임 루프 안에서 연결된다.

이번 MVP의 목표는 2인 7일이라는 제한된 기간 안에 완성도 높은 전체 서비스를 모두 만드는 것이 아니라, 한 방에서 2~4명의 플레이어가 접속해 `LOBBY -> BUILDING -> VALIDATING -> MERGING -> RACING -> RESULTS` 흐름을 끝까지 경험할 수 있는 작동 가능한 버전을 만드는 것이다. 따라서 치팅 방지, 고급 서버 물리, 복잡한 에셋 행동 시스템, 모바일 최적화보다 “게임 한 판이 안정적으로 끝나는 것”을 최우선 성공 기준으로 둔다.

## 2. MVP 핵심 방향

MVP에서 가장 중요한 판단은 기능을 무리하게 넓히지 않는 것이다. 이 프로젝트는 AI 생성, 맵 에디터, 실시간 멀티플레이, 플랫폼 물리, 방 시스템, 랭킹 시스템을 모두 포함하고 있어 범위가 매우 크다. 그러므로 AI 생성은 서비스의 매력 요소로 유지하되, 게임 진행의 필수 조건으로 만들지 않는다. 사용자가 AI 에셋 생성을 요청한 상태에서도 바로 방에 입장하고 기본 제공 에셋으로 게임을 시작할 수 있어야 한다. AI 생성 결과는 완료되면 도감에 추가되고, 다음 제작 단계에서 사용할 수 있도록 처리한다.

맵 에디터는 자유 배치 방식이 아니라 32x32 픽셀 그리드 스냅을 강제한다. 사용자가 에셋을 픽셀 단위로 자유롭게 배치하면 점프 가능 여부가 미세하게 달라지고, 타일 사이에 캐릭터가 끼거나 충돌 판정이 흔들리는 문제가 많이 발생한다. MVP에서는 모든 충돌 에셋을 그리드 단위로만 배치하게 하여 물리 버그를 줄이고, 제작된 맵이 예측 가능한 구조를 갖도록 한다. 배경 에셋도 구현 단순화를 위해 기본적으로 그리드 배치를 따르며, 추후 고도화 단계에서만 자유 시각 배치를 허용한다.

레이싱 동기화는 MVP 한정 클라이언트 권위 모델을 사용한다. 각 클라이언트는 자신의 좌표와 상태를 10~20Hz 정도로 서버에 전송하고, 서버는 이를 같은 방의 다른 사용자에게 그대로 브로드캐스트한다. 서버가 속도 검증, 데드 레코닝, 충돌 재연산, 안티치트까지 담당하는 구조는 완성도가 높지만 7일 일정에는 맞지 않는다. 대신 서버는 방 상태, 페이즈 전환, 타이머, 제출 여부, 검증 결과, 최종 순위만 권위 있게 관리한다.

## 3. 핵심 구현 기능 상세 명세

아래 항목은 본 MVP에서 구현해야 하는 핵심 기능을 원 요구사항 기준으로 다시 정리한 것이다. 기존 계획서에는 큰 흐름이 포함되어 있었지만, 아바타 생성, 방 목록 표시 필드, 맵 에디터의 세부 UI, DB 저장 맵 로드, 게임 패널티 방식 등은 명시가 부족했으므로 이 절에서 구현 기준을 정확히 고정한다.

첫째, 로그인 화면은 닉네임 입력만 제공한다. 사용자는 별도의 회원가입 없이 닉네임을 입력하고 접속하며, 서버는 임시 `user_id`를 발급한다. 닉네임은 방 목록, 대기방, 레이스 결과 화면에서 플레이어 식별용으로 사용한다.

둘째, 아바타 생성 기능을 제공한다. 사용자는 서비스 내부의 간단한 그림장에 직접 그림을 그리거나 이미지를 업로드할 수 있고, 어떤 아바타를 만들고 싶은지 텍스트로 입력한다. 서버는 그림 또는 업로드 이미지와 텍스트를 함께 받아 OpenAI API를 호출하고, 내부 WAN GPU 서버가 이해하기 쉬운 스프라이트 생성용 프롬프트로 변환한다. 이후 변환된 프롬프트와 입력 이미지를 WAN GPU 서버 API에 전달하여 아바타 스프라이트를 생성하고, 결과 이미지를 사용자의 아바타 프로필 도감에 추가한 뒤 DB에 저장한다. MVP에서는 생성이 지연되거나 실패해도 기본 아바타로 게임을 계속 진행할 수 있어야 한다.

셋째, 에셋 생성 기능을 제공한다. 에셋 생성도 아바타 생성과 같은 흐름을 사용한다. 사용자는 그림장 또는 이미지 업로드를 통해 참고 이미지를 제공하고, 만들고 싶은 에셋을 텍스트로 설명한다. 서버는 두 입력을 바탕으로 OpenAI API를 호출해 WAN용 최적화 프롬프트를 만들고, 내부 GPU 서버 API에 전달해 스프라이트를 받는다. 생성된 에셋은 사용자의 에셋 도감에 추가되고 DB에 저장된다. 에셋은 `DEVICE`, `TERRAIN`, `ENEMY`, `ITEM`, `BACKGROUND` 중 하나의 타입을 가져야 하며, 게임 로직을 위해 충돌 타입, 배치 비용, 셀 크기 정보를 함께 저장한다.

넷째, 가상 방 생성 기능을 제공한다. 사용자는 public 또는 private 유형을 선택해 멀티플레이 방을 만들 수 있다. public 방은 비밀번호 없이 입장 가능하며, “공개방 입장하기” 버튼을 누르면 현재 대기 중이고 정원이 차지 않은 public 방 중 하나에 무작위로 입장한다. private 방은 생성 시 비밀번호를 설정하고, 다른 사용자는 해당 비밀번호를 입력해야 입장할 수 있다. 로비에서는 public/private 여부와 관계없이 현재 대기 중인 방 목록을 볼 수 있어야 하며, 방을 클릭하면 해당 방 입장 절차가 시작된다. 방 목록에는 공개 여부, 생성자 이름, 현재 인원, 최대 인원, 현재 게임 상태 또는 플레이 시간이 표시되어야 한다.

다섯째, 맵 제작 기능을 제공한다. 게임이 시작되면 모든 사용자는 3분 동안 주어진 에셋을 기반으로 자신의 맵 조각을 만든다. 좌측에는 에셋 창고를 배치하고, 최상단에서 `내가 만든 에셋`과 `제공 에셋`을 전환할 수 있게 한다. 그 아래에는 `장치`, `지형`, `적군`, `아이템`, `배경` 5가지 분류 탭을 두고, 선택된 분류에 맞는 에셋 목록을 표시한다. 에셋을 드래그하면 중앙 맵 캔버스에 배치되고, 배치 가능한 충돌 에셋은 32x32 그리드에 강제로 스냅된다. 좌측 사이드바에는 작은 닫기 버튼을 두어 왼쪽으로 축소할 수 있게 한다. 좌측 하단에는 시간 추가 `+15s`, 시간 단축 `-15s`, 남은 시간, 테스트 하기 버튼을 배치한다. 시간 추가와 단축은 모든 사용자에게 동일하게 적용되며, MVP에서는 1인 1표 투표 방식과 한 페이즈당 최대 1회 제한을 둔다.

상단에는 즐겨찾기 또는 자주 사용한 에셋 창고를 둔다. 에셋은 사용 횟수가 많은 순서대로 왼쪽부터 내림차순 정렬하고, 화면 너비에 따라 표시 가능한 N개만 보여준다. 상단 에셋에 마우스를 올리면 우측 상단에 X 버튼이 나타나며, 사용자는 해당 에셋을 즐겨찾기 목록에서 제거할 수 있다. 상단 에셋도 드래그하면 중앙 맵에 배치된다. 우측에는 맵 이동, 확대/축소, 에셋 선택, 에셋 이동, 삭제 등 맵 제작에 필요한 최소 도구를 배치한다.

중앙 영역은 Phaser 기반 맵 에디터로 구성한다. 최초 맵 제작을 시작할 때는 DB에 저장된 기본 맵 템플릿을 불러오고, 시작지점과 끝지점을 표시하는 에셋이 각각 1개씩 존재해야 한다. 시작점과 끝점은 복제하거나 삭제할 수 없으며, 그리드 단위 이동만 허용한다. 맵의 최대 길이와 높이는 제한하되, 사용자는 시작점과 끝점을 이동하여 실제 사용 구간의 가로 길이를 줄이고 높이 차이를 조절할 수 있다.

여섯째, 맵 검사 기능을 제공한다. 사용자가 맵 제작을 완료하거나 제작 시간이 끝나면 해당 맵은 잠기며 더 이상 수정할 수 없다. 이후 2분 동안 사용자는 자신이 만든 맵만 대상으로 직접 플레이하여 시작지점부터 끝지점까지 도달해야 한다. 제한 시간 안에 클리어하면 해당 맵은 검증 성공 상태가 되고, 클리어하지 못하면 검증 실패 상태가 된다. 검증 실패자는 최종 레이스에서 패널티를 받는다.

일곱째, 맵 병합 기능을 제공한다. 서버는 검사 단계에서 클리어된 맵만 모아 순서를 무작위로 섞은 뒤 하나의 전역 맵으로 병합한다. 각 맵의 시작지점이 이전 맵의 끝지점과 연결되도록 X축과 Y축 오프셋을 모두 계산해야 한다. 즉, 단순히 가로로만 이어 붙이는 것이 아니라 높이 변화도 이어져야 한다. 검증에 성공한 맵이 하나도 없으면 기본 제공 맵 세그먼트를 사용하여 최종 레이스가 중단되지 않게 한다.

여덟째, 게임 플레이 기능을 제공한다. 모든 플레이어는 병합된 맵의 가장 첫 시작지점에서 출발하여 가장 끝 지점까지 레이싱을 진행한다. 기본 플레이 시간은 5분이며, 끝점에 도착한 플레이어의 도착 시간을 기록한다. 원 요구사항은 맵 검사에 실패한 플레이어에게 도착 시간 `+15s` 패널티를 부여하는 방식이다. 다만 MVP 구현 난이도와 사용자 체감을 고려하면 시작 시 15초 freeze 방식이 더 단순하다. 따라서 최종 구현 기준은 팀 의사결정에 따라 하나로 고정해야 하며, 이 계획서의 기본 결정은 기존 MVP 보정안인 `레이스 시작 시 15초 freeze`로 둔다. 원 요구사항을 그대로 따르려면 이 항목만 `도착 시간 +15s`로 변경하면 된다.

5분이 지났을 때 도착한 플레이어가 아무도 없으면 30초 추가 시간이 부여된다. 추가 시간 동안에는 각 플레이어의 현재 가로 위치를 세로선으로 표시하여 누가 가장 앞에 있는지 직관적으로 보여준다. 추가 시간 동안 도착한 플레이어가 있으면 도착 시간을 기준으로 순위를 정하고, 끝까지 도착하지 못한 플레이어는 병합된 맵의 최종 끝지점과의 거리가 가까운 순서대로 순위를 정한다.

## 4. 사용자 플로우

사용자는 먼저 닉네임만 입력하여 로그인한다. 별도의 회원가입이나 OAuth 인증은 MVP 범위에서 제외하고, 서버가 임시 `user_id`를 발급한다. 로그인 후에는 로비에서 공개방과 비공개방 목록을 확인할 수 있으며, 공개방은 비밀번호 없이 입장 가능하고 비공개방은 비밀번호를 입력해야 입장 가능하다. “공개방 빠른 입장” 기능은 현재 대기 중인 공개방 중 입장 가능한 방 하나를 무작위로 선택해 연결한다.

게임이 시작되면 모든 사용자는 3분 동안 자기 맵 조각을 제작한다. 좌측에는 에셋 창고가 있으며, 기본 제공 에셋과 사용자가 만든 에셋을 구분한다. 에셋은 장치, 지형, 적군, 아이템, 배경 유형으로 분류한다. 상단에는 자주 사용하거나 고정한 에셋 목록을 표시하고, 중앙의 Phaser 캔버스에서 실제 맵을 제작한다. 우측에는 선택, 이동, 삭제, 확대/축소 등 최소한의 제작 도구를 배치한다.

제작 시간이 끝나면 맵은 잠기고 수정할 수 없다. 이후 2분 동안 사용자는 자신이 만든 맵을 직접 플레이해 시작점에서 끝점까지 도달해야 한다. 성공하면 해당 맵 조각은 `validated` 상태가 되고, 실패하면 최종 레이스 시작 시 15초 동안 움직이지 못하는 패널티를 받는다. 검증은 제작 종료 시점의 맵 스냅샷과 `segment_hash` 기준으로 처리하여 검증 후 맵 내용이 바뀌는 문제를 방지한다.

검증 단계가 끝나면 서버는 성공한 맵 조각만 모아 무작위 순서로 섞고, 각 세그먼트의 시작점과 이전 세그먼트의 끝점을 이어 붙여 하나의 전역 맵을 생성한다. 이때 X축뿐 아니라 Y축 오프셋도 반영하여 위아래로 이어지는 릴레이 맵을 만든다. 단, 세그먼트 간 Y축 차이가 너무 커지면 카메라 이동과 플레이 난이도가 급격히 불안정해지므로 `end.y - start.y` 범위를 제한한다. 검증에 성공한 맵이 하나도 없다면 기본 제공 세그먼트를 사용하여 레이스가 무조건 진행되도록 한다.

최종 레이스는 5분 동안 진행한다. 플레이어는 병합된 맵의 첫 시작점에서 출발하고, 검증 실패자는 15초 freeze 패널티를 받은 뒤 움직일 수 있다. 누군가 끝점에 도달하면 도착 시간이 기록된다. 5분 안에 아무도 도착하지 못하면 30초 연장 시간이 주어지고, 이때 각 플레이어의 현재 X 위치를 세로선으로 표시하여 누가 앞서 있는지 쉽게 볼 수 있게 한다. 최종 순위는 완주자의 도착 시간 오름차순을 우선하고, 완주하지 못한 플레이어는 최종 끝점과의 거리 기준으로 정렬한다.

## 5. 기술 스택

프론트엔드는 `Vite + React + TypeScript + Phaser + Zustand` 조합을 사용한다. React는 로그인, 로비, 방 목록, 에셋 도감, AI 생성 폼, 결과 화면, HUD, 사이드바처럼 일반 웹 UI가 강한 영역을 담당한다. Phaser는 게임 캔버스, 물리 엔진, 충돌 처리, 카메라, 맵 에디터 렌더링, 레이스 플레이를 담당한다. Zustand는 현재 유저, 현재 방, 페이즈, 선택 중인 에셋, UI 패널 상태처럼 클라이언트 전역 상태를 가볍게 관리한다.

백엔드는 `Node.js + Express + Socket.IO + TypeScript`를 사용한다. Express는 세션 생성, 에셋 조회, 에셋 생성 요청, 방 목록, 맵 세그먼트 제출 같은 REST API를 담당한다. Socket.IO는 방 입장, 페이즈 전환, 타이머 tick, 시간 조정 투표, 검증 결과 전파, 레이스 좌표 브로드캐스트, 결과 발표를 담당한다. WebRTC는 P2P 연결, STUN/TURN, 방화벽 이슈가 있어 MVP에는 과하다. 서버 중심 Socket.IO 구조가 훨씬 단순하고 과제 시연에도 적합하다.

데이터 저장은 `PostgreSQL + Prisma`를 기본으로 한다. Prisma는 TypeScript 환경에서 DB 모델과 코드 타입을 연결하기 쉬워 개발 속도와 안정성에 도움이 된다. REST와 Socket payload는 `Zod`로 검증하여 잘못된 요청이 서버 내부 로직으로 들어가지 않게 한다. 이미지 파일은 MVP에서는 서버의 업로드 디렉터리 또는 간단한 정적 파일 저장소에 저장하고, 배포 고도화 단계에서 S3, Cloudflare R2, MinIO 같은 객체 저장소로 분리한다.

AI 연동은 서버에서만 수행한다. 브라우저는 OpenAI API 키나 내부 GPU 서버 키를 절대 알 수 없어야 한다. 사용자가 텍스트와 이미지 또는 캔버스 그림을 제출하면 서버가 OpenAI API를 호출해 WAN GPU 서버가 이해하기 쉬운 프롬프트로 정리한다. 이후 내부 GPU 서버에 비동기 Job을 생성하고, 결과가 나오면 `DONE`, 실패하면 `FAILED` 상태로 저장한다. AI 생성이 오래 걸리는 동안에도 사용자는 기본 에셋으로 게임을 계속 진행할 수 있어야 한다.

## 6. 주요 데이터 모델

`User`는 `id`, `nickname`, `avatar_asset_id`, `race_penalty_ms`를 가진다. MVP에서는 영구 계정이 아니라 임시 사용자로 충분하다.

`Asset`은 `id`, `owner_id`, `type`, `sprite_url`, `placement_cost`, `collider_type`, `width_cells`, `height_cells`, `status`를 가진다. 중요한 점은 AI가 만든 이미지를 그대로 게임 로직으로 쓰지 않는 것이다. 이미지는 시각 표현이고, 실제 충돌은 `collider_type`과 셀 크기를 기준으로 처리한다.

`MapSegment`는 `id`, `room_id`, `creator_id`, `start_point`, `end_point`, `assets`, `segment_hash`, `is_validated`를 가진다. `assets`에는 배치된 에셋 ID와 그리드 좌표가 저장된다. 제작이 끝나는 순간 스냅샷을 고정하고 해시를 만들어 검증 대상과 최종 병합 대상이 같은 맵임을 보장한다.

`Room`은 `id`, `is_public`, `password_hash`, `phase`, `players`, `max_players`, `phase_ends_at`을 가진다. 방의 페이즈는 서버가 관리하며, 클라이언트는 서버가 전파한 페이즈에 맞춰 화면을 전환한다.

## 7. 핵심 API와 Socket 이벤트

REST API는 최소한으로 구성한다. `POST /session`은 닉네임 기반 임시 세션을 생성한다. `GET /assets`는 기본 에셋과 내 에셋을 조회한다. `POST /assets/generate`는 AI 생성 작업을 등록한다. `GET /rooms`, `POST /rooms`, `POST /rooms/:id/join`은 로비와 방 입장을 담당한다. `POST /rooms/:id/segments`는 제작 완료된 맵 세그먼트를 서버에 제출한다.

Socket 이벤트는 실시간 게임 흐름을 담당한다. `room:joined`는 입장 성공을 알리고, `phase:changed`는 페이즈 전환을 전파한다. `timer:tick`은 남은 시간을 동기화한다. `segment:submitted`는 플레이어별 제출 상태를 공유한다. `validation:result`는 검증 성공/실패를 알린다. `race:position`은 클라이언트 좌표를 브로드캐스트한다. `race:finished`는 도착 이벤트를 전달하고, `results:final`은 최종 순위를 표시한다.

## 8. MVP 규칙과 제한

그리드는 32x32 픽셀로 고정한다. 충돌 가능한 에셋은 반드시 그리드에 맞춰 배치한다. 시작점과 끝점은 삭제하거나 복제할 수 없고, 그리드 단위 이동만 허용한다. 맵의 최대 폭과 높이를 제한하고, 한 세그먼트의 Y축 시작점과 끝점 차이도 제한한다. 지나치게 긴 맵, 클리어 불가능한 낭떠러지, 카메라가 따라가기 어려운 급격한 고저차를 줄이기 위한 장치이다.

시간 추가와 단축은 버튼을 누르는 즉시 적용하지 않는다. 한 명이 반복해서 시간을 조작하면 게임 흐름이 망가지므로, MVP에서는 1인 1표 방식으로 처리한다. 과반수가 찬성하면 15초를 추가하거나 단축하고, 한 페이즈에서 최대 1회만 허용한다.

검증 실패 패널티는 “도착 시간 +15초”가 아니라 “레이스 시작 시 15초 freeze”로 통일한다. 이 방식은 플레이어가 패널티를 즉시 체감할 수 있고, 결과 화면에서 계산식이 덜 복잡하다.

## 9. 리스크 관리

가장 큰 리스크는 AI 생성 지연이다. 이를 해결하기 위해 기본 제공 에셋의 품질과 수량을 충분히 확보해야 한다. 최소한 지형 타일, 점프 발판, 장애물, 배경, 시작점, 끝점, 단순 적군 정도는 기본으로 제공해야 한다. AI 생성이 실패하거나 지연되어도 게임의 핵심 루프가 멈추지 않아야 한다.

두 번째 리스크는 물리 버그다. 이를 줄이기 위해 자유 배치를 금지하고 그리드 스냅을 강제한다. 또한 MVP에서는 복잡한 회전, 비정형 충돌체, 경사면, 움직이는 플랫폼을 최소화한다. 필요한 경우 지형과 장애물은 사각형 충돌체 위주로 구현한다.

세 번째 리스크는 멀티플레이 동기화다. 서버 권위 물리는 이상적이지만 일정상 부담이 크다. MVP에서는 클라이언트 권위 모델로 가고, 서버는 좌표를 그대로 중계한다. 이 결정은 치팅 방지를 포기하는 대신 시연 가능한 멀티플레이 완성도를 확보하기 위한 현실적인 선택이다.

Day 4에는 페이즈 상태 머신, 타이머, 제작 종료 잠금, 검증 플레이를 구현한다. Day 5에는 맵 병합, Y축 오프셋, 레이스 화면, 좌표 브로드캐스트를 구현한다. Day 6에는 AI 생성 Job 흐름, 에셋 도감, 기본 에셋 보강, 결과 화면을 구현한다. Day 7에는 버그 수정, 시연 시나리오 정리, README와 발표 자료를 완성한다.

## 11. 테스트 계획

방 기능은 공개방 생성, 비공개방 생성, 비밀번호 오류, 빠른 입장, 최대 인원 제한을 확인한다. 페이즈 기능은 로비에서 제작, 검증, 병합, 레이스, 결과까지 자동으로 넘어가는지 확인한다. 맵 에디터는 그리드 스냅, 비용 제한, 시작점/끝점 삭제 불가, 잠금 후 수정 불가를 확인한다. 검증 기능은 성공 시 `validated = true`, 실패 시 패널티 적용을 확인한다. 병합 기능은 서로 다른 Y축 값을 가진 맵들이 끊기지 않고 연결되는지 확인한다. 레이스 기능은 좌표 브로드캐스트, 완주 기록, 30초 연장, 미완주자 거리순 정렬을 확인한다. AI 기능은 생성 성공, 실패, 지연 상태에서도 기본 에셋으로 게임을 진행할 수 있는지 확인한다.

## 12. 최종 성공 기준

최종 산출물은 실행 가능한 웹 앱이어야 하며, 최소 2명의 사용자가 같은 방에 접속해 맵 제작부터 최종 레이스 결과까지 한 번의 게임을 끝낼 수 있어야 한다. AI 에셋 생성은 시연에서 보여줄 수 있으면 좋지만, GPU 서버 지연이나 실패가 있더라도 기본 에셋 기반 게임 루프가 반드시 동작해야 한다. 이 MVP의 본질은 모든 기능을 완벽하게 만드는 것이 아니라, “AI로 만든 재료와 사용자가 만든 맵이 실제 멀티플레이 레이스로 이어진다”는 경험을 명확하게 증명하는 것이다.
